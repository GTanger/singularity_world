## 一、設計哲學總結

在《奇點世界》的底層架構中，為了實現「萬人萬相 (SoulSeed)」並讓 NPC 擁有如真人般的動態流動與湧現行為，我們打破了傳統 RPG 中將「職業」或「身份」作為變數寫死在角色身上的做法。

系統的核心運作公式可以總結為：

**[ 本體狀態 (State) ] + [ 情境指派 (Assignment) ] = 系統行為 (Code Logic) ➡️ 玩家觀測到的「身份」(Identity)**

---

## 二、三者概念解析

### 1. 狀態 (State) —— 絕對的、內在的、自身定義的

**狀態**是系統運算的最底層基石，代表實體（Entity）客觀存在的資料。

*   **本質**：角色當下擁有的一切變數。包含：背包庫存、持有的鎂（貨幣）、生命值與各項屬性、SoulSeed 賦予的性格傾向；廣義上也可包含**當下正在執行的原子動作**（如：正在移動、正在攻擊）——此時狀態即「可查詢的當下 snapshot」，與事件／行為層在概念上互補（持久資料 vs 當前行為）。
*   **系統作用（需求驅動）**：狀態是觸發一切行為的根源（Needs-Driven）。角色不會因為「我是員工」而工作，而是因為「狀態顯示：鎂餘額極低，即將無法支付食物消耗」，進而觸發了「尋找工作」或「乞討」的行為意圖。
*   **特性**：客觀存在，不依賴外界觀測。即便是獨自一人處於密室，狀態依然持續運算。

### 2. 指派 (Assignment) —— 情境的、結構的、代碼邏輯的銜接層

**指派**是連接「狀態」與「外部世界（場所）」的數據橋樑。它不是標籤，而是一種**暫時性的槽位綁定**。

*   **本質**：將特定的實體（NPC/玩家）與特定的場所（Venue）及職務（Occupation）連結的資料結構（如 `Assignment{EntityID, VenueID, OccupationID}`）。
*   **系統作用（插頭插座匹配）**：對代碼邏輯而言，系統只看此實體是否有對應的指派紀錄。如果有，系統就在該場所的範圍內（`room_ids`），為這個實體開放特定的**動作插座 (Sockets)**（如：`Manage`、`Trade_at_counter`）並掛載對應的對話模板。
*   **特性**：解耦了角色與職業。拔除這個指派數據，角色立刻失去相關的插座與職能。

### 3. 身份 (Identity) —— 相對的、外在的、被觀測而來的

**身份**是在前端 UI 呈現、對話文本與玩家認知中，對於上述複雜底層邏輯的一種**簡化標籤與觀測結果**。

*   **本質**：基於「狀態 + 行為 + 指派的環境」動態推導出來的結果。它不是存放在資料庫裡的一個獨立字串（即便過渡期有 `display_title`，其語意也是推導而來）。
*   **系統作用（認知呈現）**：
    *   **對玩家**：當玩家走進客棧，看見某個實體（狀態）站在櫃台後方（場所），且系統因為其擁有 `Assignment` 而對玩家彈出了「辦理入住」的互動選項（插座），玩家自然在腦海中（以及 UI 標題上）產生了「他是客棧經理」的**身份認知**。
    *   **對 LLM / 對話庫**：當系統需要生成對話時，會將「你現在被指派為客棧經理」作為前情提要（Context）餵給對話模型，從而產出符合該「身份」的語氣。
*   **特性**：身份是外在眼光賦予的。如果一個客棧經理下班後（脫離了 Venue 範圍或撤除了 Assignment），走在街上，沒有特定的職務插座，此時在他人眼裡，他的身份就會消散或轉變為「平民」或「路人」。這正是湧現式設計的魅力。
*   **UI／API 上的輸出**：身份作為「觀測結果」仍需轉成**顯示用字串**（如人物欄職稱、對話前情）。實作上由**當前有效指派**推導（如 `GetNPCTitle` 依 Assignment + Occupation）；無指派時 fallback 為 `display_title` 或預設「路人」等，與 [玩家視角—NPC 與房間互動](玩家視角—NPC%20與房間互動.md) 人物欄顯示、[討論 001](../discussions/001_身份與職業分離—角色無身份綁定.md) 對齊。

## 三、架構面的優勢（為何不直接寫死身份？）

1.  **實踐「需求驅動 (Needs-Driven)」與社會流動**：
    (參考 [討論 002](../discussions/002_NPC需求驅動與求職機制.md))
    如果寫死 `NPC.Identity = "Manager"`，系統邏輯會變成一套僵硬的狀態機。但依靠「狀態 + 指派」，當客棧倒閉（Venue 消失）或 NPC 發現採集利潤更高（狀態改變），NPC 可以自然放棄這個 Assignment。此時他的外在身份自動從「經理」轉變成「無業遊民」或「採集者」，無需額外的複雜重置邏輯。
2.  **落實「職務插座」與行為語義**：
    (參考 [討論 001](../discussions/001_身份與職業分離—角色無身份綁定.md))
    這種作法完美契合本專案的「插頭插座」原則。職務行為不是「某個人天生會做的事」，而是「在某個特定場所，佔據了某個職缺後，系統賦予的動作權限」。
3.  **無職謀生（如：行腳商）的自然湧現**：
    一個沒有任何工作指派的 NPC，如果他的狀態是「帶著大量低買高賣的貨物在不同城鎮間移動並開放 Trade 插座」，那麼路過觀測到他的玩家，自然會給予他「行腳商」的**身份**。這裡完全不需要 `OccupationID = "Peddler"` 的指派。本專案將 **Trade 列為 Agent 預設插座**（見 [決策 002](../decisions/002_sockets_plugs_semantic.md)），故無指派時 NPC 與**玩家**皆具備 Trade；玩家在 A 地買、B 地賣，行為上即為行腳商，身份由觀測湧現，與 NPC 一致。

## 四、與背版、記憶的關係

| 概念 | 定位 | 說明 |
|------|------|------|
| **身份** | 當下情境下的角色標籤 | 由「狀態 + 指派 + 場所」推導，回答「此刻在玩家眼中他是誰」（經理、路人、行腳商）。 |
| **背版 (Backstory)** | 跨情境的個體設定 | 如 identity / summary / relationship blocks，描述「這個人是誰、與世界／玩家的關係」，供對話與記憶檢索使用。 |
| **記憶 (Archival)** | 跨情境的個體史 | 過往事件、對話要旨，依 `entity_id` 檢索，讓下次見面時回覆能延續。 |

身份側重**當下被觀測到的角色**；背版與記憶側重**跨時間、跨情境的個體脈絡**。三者互補：身份決定「現在稱他什麼、能對他做什麼」，背版與記憶決定「他會說什麼、記得什麼」。

## 五、對話模板與「預設身份」的關係

**你提出的張力**：目前有**公版對話**（不綁身份），其餘對話卻都綁定「身份」（經理、服務生、鐵匠…），等於**得先預設出身份，才能設計對話模板**。這是否與「身份由觀測湧現」矛盾？

### 5.1 釐清：我們預設的是「職務類型」，不是「把身份寫在角色身上」

| 層次 | 說明 |
|------|------|
| **內容設計時** | 我們預先定義的是**世界上有哪些職務類型 (Occupation Types)**，以及「每種職務類型用哪一份對話／行為模板」。例如：`occupations.json` 裡有「經理」「服務生」，各自對應 `dialogues/manager.json`、`dialogues/waiter.json`。這是**世界提供的槽位與內容**，不是「某個 NPC 叫經理」。 |
| **運行時** | 角色身上**不寫死身份**。某個實體是「經理」或「路人」，是因為他**被指派到某個場所的經理槽位**，或**沒有指派、僅有公版**。身份是插上槽位後被觀測到的結果。 |
| **設計順序** | 因此順序是：**(1) 定義職務類型與其對話／行為模板**（經理說什麼、服務生說什麼、鐵匠說什麼）→ **(2) 場所提供這些職務槽位** → **(3) NPC／玩家經由指派或行為佔據槽位** → **(4) 玩家觀測到「他是經理／行腳商」**。我們沒有「先給每個 NPC 一個身份再寫對話」，而是「先定義世界有哪些角色類型與其內容，再讓實體去佔據這些類型」。 |

所以：**對話模板綁定的是「職務類型」這套詞彙，不是綁定在單一角色上**。預設身份 = 預設**世界上有哪些槽位與每槽的內容**；誰佔據哪個槽位是運行時由指派與行為決定的。

### 5.2 公版 vs 職務綁定：兩層並存

| 類型 | 用途 | 設計時機 |
|------|------|----------|
| **公版對話** | 無指派、或無法對應到任一職務類型時使用（fallback）；任何人都有機會用到。 | 先做一組「不帶身份」的通用句，避免空白或錯用他職模板。 |
| **職務類型對話** | 當實體**被指派到該職務**且在場時使用（如經理、服務生、鐵匠）。 | 依「世界上有哪些職務類型」逐類設計；每類一至多檔，key 用 greet／talk／idle 等。 |

兩者並存不矛盾：公版負責**保底與無職情境**，職務類型負責**有指派時的情境**。設計對話時的確需要「先列出我們要支援哪些職務類型」，但那是**內容詞彙的設計**，不是「先給每個 NPC 填上身份欄位」。

### 5.3 若想減少「先列出一堆身份」的感覺（可選）

若希望對話設計更偏「情境／行為」而非「職務名稱」，可以輔助做法例如：

- **情境維度**：同一職務下再細分情境（如在櫃台、在搬貨、剛下班），依場所或狀態選不同 line 子集。
- **行為維度**：部分句子依「當前行為」選（例如正在移動、正在交易），與職務類型疊加使用。

主軸仍建議保留**職務類型**作為對話模板的索引，否則「純情境／純行為」會導致模板數量爆炸、難以維護。職務類型 = 世界槽位的設計詞彙，身份 = 誰佔據哪個槽位的觀測結果，兩者分開即可。
