# 討論 004：Web LLM 調度與複數玩家

> **目前結論**：壓力測試顯示本地 LLM 完全稱得住；**NPC 間對話依然排隊**，**玩家與同房 NPC 對話不排隊、直接打本地 LLM 併發**。Web LLM 留作**佔位預設**，暫不實作。  
> 對齊：[003 NPC 交互對話系統](003_NPC交互對話系統.md)（玩家優先 LLM、NPC-NPC 用本地）。

---

## 一、方案摘要與目前策略

| 角色 | 使用 LLM | 目前策略 |
|------|----------|----------|
| **玩家對 NPC 對話** | 本地 LLM | **不排隊**：玩家 Talk 直接送本地 LLM，與 NPC 間對話或其它玩家 Talk **併發**；同房有無 NPC 在對話不影響玩家。 |
| **NPC 間對話** | 本地 LLM | **排隊**：觸發時送進本地佇列（一次一筆或有限併發），不與玩家搶優先。 |
| **Web LLM** | 遠端 API | **佔位預設**：config／介面預留 endpoint、key 等，**目前不實作**；日後若本地滿載或要分流再啟用。 |

**設計要點**：
- 玩家體驗：同房內玩家可隨時與 NPC 對話，無須等 NPC 間對話跑完；本地 Ollama 可並行多筆，玩家 Talk 與 NPC-NPC 可同時在飛。
- 目前壓力稱得住：見 §六 壓力測試與資源觀察。
- 複數玩家見下節；Web 選項（A/B/C/D）保留供日後啟用時參考。

## 二、複數玩家時的情境與選項

當同服／同世界有**多名玩家**時，「僅玩家有權用 web LLM」會衍生：誰算「玩家」、誰在「本地忙碌」時可走 web、以及 web 用量如何控管。

### 2.1 情境簡述與「本地是否只能單筆」的澄清

- **本地 LLM 併發能力**：**並非**必然「同一時間只能處理一筆」。以 Ollama 為例，能否同時處理多筆請求取決於實例設定與資源（例如 `OLLAMA_NUM_PARALLEL`、顯存／模型大小）。若本地可並行 N 筆（N≥2），則：
  - **複數玩家在不同地**（不同房間、不同 NPC）同時 Talk → 可**同時**都打本地 LLM，不必搶單一槽位，也未必需要 web。
  - 「**忙碌**」應定義為：**目前進行中的本地請求數已達上限**（例如 N 筆在跑），而非「只要有任一筆在跑就算忙碌」。
- **Web LLM**：遠端 API，通常有 key、QPS／併發或月額限制；用於**本地已滿載**（或你選擇「本地一有請求就讓玩家走 web」）時支援玩家。
- **複數玩家**：多人同時在線、且本地**已滿載**時，才需決定誰走 web、誰排隊等本地；若本地可並行多筆，則「不同地的玩家同時對話」可都由本地處理，無須動用 web。

### 2.2 選項 A：所有玩家在「本地忙碌時」皆可走 Web

- **規則**：不區分玩家身份；只要**當前請求是「玩家對 NPC 的 Talk」**且**判定本地忙碌**，就改打 web LLM。
- **優點**：實作簡單、公平（誰先點誰先得到 web 支援）。
- **注意**：  
  - Web 用量 = 所有玩家的此類請求；人數多或頻繁對話時，key 額度／QPS 可能吃緊。  
  - 若 web 也有併發上限，可能需對「走 web 的玩家 Talk」做**佇列**（先到先服務）或限流（例如每玩家 N 秒一筆），避免 key 爆掉或 429。

### 2.3 選項 B：僅「特權玩家」可走 Web（白名單）

- **規則**：設定一份**允許使用 web LLM 的 player_id 白名單**（或由你一人持有 key，僅自己登入的 id 在白名單）。本地忙碌時，僅白名單內玩家的 Talk 走 web；其餘玩家排隊等本地。
- **優點**：用量完全可控（只有你會觸發 web）；複數玩家時，其他人不會消耗你的 key。
- **注意**：  
  - 需維護白名單（config 或後台），以及「當前連線的 player_id 是否在白名單」的檢查。  
  - 非白名單玩家在本地忙時會等較久，體感可能較差，可視為設計取捨。

### 2.4 選項 C：Web 有獨立併發上限，先到先服務

- **規則**：所有玩家在本地忙碌時都可**嘗試**走 web，但 web 端有**全域併發上限**（例如同時最多 1 筆或 2 筆）。若當前已達上限，後到的玩家 Talk 改為**排隊等 web**（或排隊等本地，視你希望「等 web」還是「等本地」）。
- **優點**：用量與負載可控，多人時不會無上限打爆 web API。
- **注意**：  
  - 需實作「web 請求佇列」或 semaphore；若選「等 web」，要定義逾時（等太久可 fallback 本地或模板）。  
  - 若「等本地」：則等同本地忙時，第二個玩家也等本地，與單一佇列類似。

### 2.5 選項 D：每玩家限頻（rate limit）＋ 其餘同 A

- **規則**：與 A 相同，但對「走 web 的請求」做**每玩家**的限頻（例如同一玩家 30 秒內最多 1 筆走 web）。超過則該次 Talk 改排隊等本地（或 fallback 模板）。
- **優點**：避免單一玩家狂點耗盡 key；多人時每人可偶爾用 web，其餘走本地。
- **注意**：需記錄每玩家上次走 web 的時間（或次數），並在 handler 內判斷。

## 三、建議收斂（可依實作階段選）

| 階段 | 建議 | 說明 |
|------|------|------|
| **目前** | **不實作 Web LLM**；玩家 Talk 直接打本地併發，NPC-NPC 排隊。Web 僅在 config／介面**佔位預設**。 | 壓力測試（三十地三十玩家十輪）顯示本地稱得住；玩家可無視 NPC 間對話、直接與同房 NPC 對話，本地 LLM 併發處理。 |
| **之後若啟用 web（key 僅自用）** | 採 **B（白名單）**：僅白名單 player_id 在本地滿載時走 web。 | 用量與權限清晰。 |
| **之後若啟用 web、多人共用** | 採 **A**，並加 **web 併發上限或每玩家限頻**（C 或 D）。 | 公平、可擴展，需佇列或限頻。 |

## 四、實作依賴（目前：Web 佔位，玩家併發、NPC 排隊）

- **配置**：Web LLM 的 endpoint、key 等留作**佔位預設**（例如 `web_llm`、空字串或未設定），**目前不接真實呼叫**。
- **玩家 Talk**：**直接**呼叫本地 LLM（`CallAITalk`），不檢查「本地是否忙碌」、不排隊；與 NPC-NPC 或其它玩家 Talk **併發**，由 Ollama 自行並行處理。
- **NPC-NPC**：觸發時送進**本地佇列**（一次一筆或有限併發），不與玩家搶；佇列內依序打本地 LLM。
- **之後若啟用 Web**：可再加「忙碌判定」（in-flight 數 ≥ N 時玩家改走 web）、白名單等，依 §二 選項細化。

## 五、複數玩家在不同地 × 本地併發

- **關鍵**：本地 LLM 是否「同一時間只能處理單筆」要看**實例與設定**，不是預設為 1。
- **若本地可並行 N 筆（N≥2）**：  
  - 玩家 A 在甲地、玩家 B 在乙地，兩人同時對各自 NPC Talk → 兩筆可**同時**送本地，不需排隊、也不需動用 web。  
  - 只有當「進行中的本地請求數 ≥ N」時，才需把多出來的請求改走 web 或排隊。
- **若本地確為單筆**（N=1）：  
  - 任一筆（玩家 Talk 或 NPC-NPC）在跑時，其他請求都需排隊或改走 web；此時「複數玩家在不同地」仍會互搶那一個槽位，需依前述選項（A/B/C/D）決定誰走 web。
- **實作建議**：config 可提供「本地最大併發數」或「是否允許多筆並行」；忙碌判定改為「當前 in-flight 數 ≥ 該上限」再觸發 web 或排隊。

專案內**不再附帶**自動化 Ollama 壓力測試；若需驗證併發，請自行以多客戶端呼叫 `CallAITalk` 或 Ollama API，並以系統監控觀察 GPU／VRAM。

## 六、高併發時資源觀察（參考）

若以本機 Ollama 做**手動／自架**高併發抽樣，常見觀察為：瓶頸多在 **GPU 算力**，VRAM 與 CPU 往往仍有餘裕（依機型與模型而異）。玩家與 NPC 對話直接併發打本地、NPC 間對話排隊，實務上可行；Web LLM 留作佔位即可，暫不實作。
