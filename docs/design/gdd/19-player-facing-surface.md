# 19 玩家表層與回饋

狀態：細節設計草案；舊文字主畫面骨架已被 2026-07-13 的 2D 大地圖方向取代
第一權威：`../../DESIGN_KEYWORDS.md`
用途：補 GDD 的「皮」。本檔只定玩家畫面與文字回饋規格，不定 CSS 或 runtime 實作。

## 表層定位

玩家表層不是裝飾，也不是後端資料欄位排版。它要讓玩家不用讀文件就能知道：

- 我是誰。
- 我在哪。
- 我手上有什麼。
- 我能點什麼。
- 做了會改變什麼。
- 為什麼下次回來會不同。
- 為什麼現在值得點下一步。

表層也必須服從 `../../DESIGN_KEYWORDS.md` 與
`21-2d-open-world-primary-surface.md`：2D 平面大地圖、輕操作、重體驗、
全物件化、後端真理、NPC 同律、永遠在線、真實經濟與
探索／冒險／經營／建造／戰鬥，都要轉成地圖上的可見入口和回饋，
不能只藏在文件、文字敘事或資料表裡。

下列「第一屏骨架」是舊文字表層素材，只能拆取資訊需求；其區塊布局、
核心入口數量與文字比例尚未被使用者接受為 2D 大地圖 HUD。

## 第一屏骨架

```text
[全局上下文]
時段 / 時間 / 天氣或局勢

[自身入口]
姓名
鎂
手持/工具
明顯狀態
近期事件摘要

[場景狀態]
地點名
當前局勢 2-4 句
可讀痕跡 0-2 句

[核心入口]
人物 0-2
物件 1-3
出口 1-3

[事件流]
最近行動結果或自然察覺到的局部變化
```

第一屏不得：

- 把玩家自己放進人物列表。
- 把錢、背包、工具塞成姓名旁雜訊。
- 顯示 debug、後端欄位、精確人群數。
- 顯示完整元素表、需求條或狀態條。
- 用一段大散文代替可點入口。
- 用沉浸、活世界、有生命感等抽象詞代替玩家畫面上可讀的狀態與後果。

第一屏必須先成立三件事：

1. 玩家知道自己是誰、在哪、身上有什麼、能做什麼。
2. 玩家能點一個入口，做出至少一個世界狀態改變。
3. 回饋讓玩家知道下一步為什麼不同，或下次回來會看到什麼痕跡。

## 自身入口呈現

自身入口最少要能展開：

```text
codex
所在地：北岸渡口
鎂：12
手持：火折
背包：油布、短繩、空包
明顯狀態：無傷；剛到此地，尚未被多數人認得
近期事件：你剛收起火折；守棚人看見了
可做：握持 / 收起 / 整理 / 休息 / 等待 / 離線安排
```

自身入口的重點是「我現在能靠什麼行動」，不是把角色資料表暴露出來。

## 場景狀態呈現

場景狀態要分三種句子：

| 句型 | 用途 | 範例 |
|---|---|---|
| 骨架句 | 這裡是什麼地方 | `北岸渡口貼著河霧，踏板通向停靠處。` |
| 局勢句 | 當下正在改變什麼 | `雨後泥深，兩個搬運者把貨改挪到棚下。` |
| 痕跡句 | 世界之前發生過什麼 | `燈架旁的油布被人收起，只剩一段濕繩掛在木樁上。` |

場景句要避免：

- 只寫氣氛。
- 只寫景物。
- 只寫 NPC 站著。
- 用地名代替狀態。
- 用陌生詞或尷尬詞壓縮設計。
- 只讓作者覺得有氛圍，玩家看不出能做什麼。

## 入口呈現

入口不是清單湊數。每個入口都要有玩家能理解的理由。

人物入口：

```text
【守棚人】看著棚邊燈架，手邊放著一卷油布。
```

物件入口：

```text
【未亮燈架】燈盞還乾，旁邊有半截舊火繩。
```

出口入口：

```text
【踏板口】霧裡只能看見近處木樁；點燈後可辨得更清。
```

不合格入口：

```text
【路人】
【木板】
【北】
```

除非點開後有狀態、動作、條件、後果，否則不要佔核心入口。

## 動作面板呈現

點入口後，動作面板顯示四件事：

```text
觀察：
你看見什麼狀態。

可做：
目前可用動作。

做不到：
若顯示不可用動作，要說世界原因。

風險：
可能失去什麼、惹到誰、錯過什麼。
```

範例：

```text
【未亮燈架】
觀察：燈盞還乾，但火繩短。棚邊守棚人看著這裡。
可做：點燈 / 問守棚人 / 暫時不碰
做不到：拿走燈架；這是棚邊公物。
風險：未問就點燈，守棚人可能要求你負責看火。
```

## 事件流呈現

事件流記錄玩家行動和局部世界變化，不是聊天刷屏。

合格事件：

```text
你收起火折，手上空了出來。
守棚人看了你一眼，沒有再攔你靠近燈架。
雨停後，踏板口的人群往前挪了一步。
```

不合格事件：

```text
world_tick updated room_state.
還有 46 人。
NPC_1032 changed schedule.
```

事件流要短，但要能回扣世界事實。

事件流還要回答玩家角度的下一步：這次變化讓哪個入口、人物、物件、路線、關係或風險變得不同。若事件流只記錄一句發生了什麼，卻不影響玩家之後的判斷，降為風味文字。

## 成功回饋

成功回饋要說清楚三件事：

```text
你做了什麼。
哪個世界事實變了。
下一個選擇因此怎麼變。
```

範例：

```text
你點亮棚邊燈架。踏板口的木樁與濕繩清楚了些，【踏板口】現在可辨路況；守棚人把油布往你這邊推了半寸。
```

## 失敗回饋

失敗不是「不能」。失敗要揭露準備方向。

範例：

```text
火繩被雨打濕，火折只擦出一點白煙。你需要先找乾繩，或問守棚人借火。
```

失敗要避免：

- `操作失敗`
- `條件不足`
- `無法使用`
- 只說系統原因，不說世界原因。

## 被搶先/錯過回饋

世界不是等玩家。錯過也要是內容。

範例：

```text
你還在看燈架時，搬運者已把兩袋怕潮的貨拖進棚內。收貨人把木牌翻到「暫停」那面。
```

錯過要接到：

- 需求變化。
- 報價變化。
- NPC 記憶。
- 路線變化。
- 可回訪痕跡。

## 重訪回饋

重訪不能只換一句場景句。

範例：

```text
棚邊燈架還亮著，但火繩只剩一小截。守棚人認出你，先指了指油布，再看向還沒搬完的貨。
```

這句同時回饋：

- 上次點燈留下的狀態。
- 工具消耗。
- NPC 記憶。
- 新入口。

## 皮層驗收

玩家表層進 runtime 前要通過：

1. 玩家能在第一屏看見自己，不只是地點。
2. 玩家能點自己，並做至少一個改變狀態的自身動作。
3. 每個核心入口都有狀態、動詞或風險。
4. 成功回饋說出世界事實差異。
5. 失敗回饋說出下一步準備方向。
6. 錯過/被搶先不是懲罰訊息，而是世界推進。
7. 重訪看得出前次行動或場外推進。
8. 沒有 debug、後設語、精確人群數或資料庫語言。
9. 玩家能說出自己下一步想點什麼，以及為什麼。
10. 表層內容能反查 `DESIGN_KEYWORDS.md`，不是由局部場景、材料或功能 NPC 硬湊。
11. 若玩家角度無感，即使 UI 清楚、文字漂亮，也不得宣稱玩家體驗完成。

## 和 runtime 的邊界

本檔不指定 CSS、DOM、Rust struct 或資料庫欄位。它只指定玩家表層必須呈現的設計結果。真正進 runtime 前，仍需依 `./start`、`cargo check`、前端檢查與 Browser/Puppeteer 畫面驗收。
