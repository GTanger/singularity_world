# 資源點設置與產出——實作建議

> **定位**：在 [資源點與礦區設計](資源點與礦區設計.md)（世界觀＋能量密度＋固定點／浮動品質）已定案的前提下，補上**空間如何掛點**、**產出如何對表**，供程式與資料管線落地。  
> **狀態**：實作草案——需設計者確認欄位與分級後再寫入 store／遷移。  
> **校正（2026-04）**：採集相關權威物理僅 **有念者念場干擾 能量輻射**（密度／生長節奏等）。本文件舊稿若曾出現「玩家與資源點對頻決定品質」已撤銷，以下欄位表已同步。  
> **設計者定案（2026-04）**：**捨棄「所有礦點都能出產所有礦物」（all-in-one）**——擇一貫徹；礦種與掉落由 **區域規則＋節點 `yield_pool`** 分區配置，可規劃多種礦點格與生成邏輯，**不保留**全表萬能節點路線。  
> **富態化**：屬世界觀物理，用於說明 **生長、再生節奏、環境危險與尺度**，**不是**用來合理化「同一節點無條件萬能產出」的作弊鍵。物質／物種的**限制框架**在富態化前後仍為同一套邏輯，僅**框架連同尺度一併富態化**；見 [世界觀：富態與拉鋸](../reference/世界觀：富態與拉鋸.md) §一「限制框架的連續性」。

## 二、設置建議（空間錨點）

### 2.1 原則

1. **權威座標以 Hex 為準**（與 `AGENTS.md`、玩家 `hex_q`/`hex_r` 一致）：資源點應能表達為 **`(world_id 或契約, q, r)`** 或等價的 `cell_id`，避免「只有 room_id、沒有世界位置」的選單式採集。
2. **一點一錨**：每個資源點一個穩定 id（例如 `resource_node_id` UUID 或字串），便於 NPC 尋路、玩家記路、經濟統計。
3. **語意分層**：  
   - **區域級**（野外分級規格）：決定「這一带允許哪些類型節點、密度下限」；  
   - **節點級**（本文件）：決定「這一格上具體是哪一種產出池、危險係數」等（**不含**「玩家與點對頻」；見文首校正）。

### 2.2 與 Room／城市的關係

| 場景 | 建議 |
|------|------|
| **Hex 格網** | 節點直接綁 `cell_id`（或 q,r）；`room_id` 可選，僅作敘事／舊 API 兼容。 |
| **地下礦區**（既有敘事） | 綁 `cell_id` + 山緣採掘帶（聚落五級 §4.8/§9.7）；MVP 可一格一節點簡化。 |
| **城鎮邊緣農田**（農業 P2） | 綁在「聚落外緣」標記的 hex 或語意房；產出走「低能量穩定」表（對齊農業概念）。 |

### 2.3 資料欄位草案（待 schema 定案）

下列為**邏輯欄位**，實作時可併入 `data/config/` JSON 或 PostgreSQL 表，**不強行假設表名**。

| 欄位 | 說明 |
|------|------|
| `id` | 節點唯一 id |
| `kind` | `mine` \| `wild_gather` \| `water` \| `farm` \| `special`（可擴充） |
| `cell_id` 或 `(q,r)` | 世界格錨點 |
| `yield_pool_id` | 指向產出池（見 §三） |
| `danger_rating` | 環境危險度 0～1 或 1～5 級，影響遭遇／損耗敘事與數值 |
| `renew_base` | 與 能量密度相乘前的基礎再生係數（對齊既有「再生速率」敘事） |
| `active` | 是否啟用（維護／事件用） |

### 2.4 設置流程建議（管線）

1. **Hex 格網** 已有格點 → 在編輯器或腳本中 **挑格** → 填 `kind` + `yield_pool_id`（及危險、再生係數等）。  
2. **與場所分級規格對拍**：該格所屬區域必須允許該 `kind`（例如深野才允許高危高產池）。  
3. **版本化**：節點表與 `world_seed`／地圖版本一併記錄，避免半套資料。

## 三、產出建議（yield_pool）

### 3.1 概念

- **產出池** = 一次「採集成功結算」時，從中**加權抽樣**，產出**材料**（白板物質）。
- **設計者定調（2026-04）**：採集只產材料。品階（丙／乙／甲）在剝名時判定，提取成數在提出時由功法決定。完整管線：採集→材料→剝名→結晶→提出→裸詞元（見 [資源點與礦區設計](資源點與礦區設計.md)）。

### 3.2 材料分類（2026-04-08 定案）

**材料不設中間子分類**。只有五大來源類 + 產地節點 ID：

| 欄位 | 說明 |
|------|------|
| `source_class` | `mineral` / `beast` / `plant` / `water` / `gas`（五大來源類） |
| `source_node_id` | 來自哪個資源節點（攜帶地理、生態、詞元權重池等所有資訊） |
| `weight` | 物理重量（負重計算用） |

不設「鐵礦石」「銅礦石」「靈石」等中間種類——能量烙印本質混沌，材料外觀不決定內容。玩家以「品階＋產地」辨識材料價值（如「蒼嶺深谷的礦石」vs「城鎮地下的礦石」）。

獸類材料 = 獸體/肢體本身，獸種即分類，不需額外標籤。

### 3.3 產出池表結構草案

| 欄位 | 說明 |
|------|------|
| `yield_pool_id` | 池 id |
| `entries` | 陣列：每項含 `source_class`、`weight`（抽樣權重）、`qty_range`（數量範圍）；**不含**品階 |
| `notes` | 給企劃／平衡用短註 |

### 3.4 與 `word_elements.json` 的對接（剝名層）

- 材料本身**不**直接對應詞元 id。對接發生在**剝名時**：系統查 `source_node_id` 對應的詞元權重表，從 500 詞元中按權重抽樣
- 每個資源節點配一張**詞元權重表**（`stripping_weights`），定義該產地材料剝名時各詞元被抽中的機率偏向
- 產地決定權重偏向，但不鎖死結果（能量烙印混沌本質）
- `gamedims` 對齊在詞元層處理，採集/材料層不涉及

### 3.4 數量與分層（建議預設）

| 項目 | 建議 | 備註 |
|------|------|------|
| 單次採集掉落數 | 先 **1 主掉落** ±0（後續再加協作／工具加成） | 節奏與念場／密度另表 |
| 丙／乙／甲 | **剝名時**擲骰判定 | **採集結算不出品階** |
| 提取成數 | **提出時**功法決定（3~9 成） | **採集/剝名均不涉及** |
| 空池 | 不允許——池至少一筆 weight>0 | 避免採集壞檔 |

## 四、類型分級與建議產出方向

以下為 **建議方向**，實際詞元 id 需對照 `data/config/word_elements.json` 填表。

| kind | 敘事定位 | 危險度 | 產出方向（示例性） |
|------|----------|--------|-------------------|
| `mine` | 地下／露天礦脈，人力協作、脈衝採集 | 中～高（坍塌／魔物） | 偏礦／石／金屬**材**；好壞**剝名時**定 |
| `wild_gather` | 野外富態化植株／殘骸 | 高（獸鏈、環境） | 偏植／獸材；稀有度可在掉落表調，**非**品質階 |
| `water` | 水域（待世界觀細化） | 中 | 偏水／流／寒等材；與剝名流程銜接 |
| `farm` | 聚念場邊緣（P2） | 低 | 低波動、高穩定產出（對齊農業概念）；品階仍剝名定 |
| `special` | 劇情／遺跡／一次性 | 依劇情 | 手工配置池 |

## 五、能量密度與採集結算（接線提醒）

- **再生**：`再生速率 = renew_base × token_density(cell)`（密度計算見資源點與礦區設計）。  
- **採集速度／敲擊數**：沿用文檔草案「基礎敲擊／在場人數」——實作時需單測平衡，**不與 store 結構綁死**。  
- **壟斷不可能**：無需額外規則模組，人在場即壓密度——節點腳本勿再加「工會專屬刷新」類與悖論衝突的規則。

## 六、待設計者拍板清單

1. **採集掉落**（種類／件數）與念場、危險等如何掛鉤；**丙乙甲不在此列**（剝名管線）。  
2. 首批 **P0 節點數量**（例如每生物群系 N 個試點）。  
3. **水域／其他**是否併入 P0 或拆到 P1。  
4. 地下礦區 **MVP**：山緣採掘帶格式是否可接受（見聚落五級 §4.8/§9.7）。

---

## 七、建議實作順序（工程）

1. 固定 **yield_pool** 與 **resource_node** 的**唯讀**資料結構與載入（只讀配置，不改玩家存檔 schema 前先與設計者確認）。  
2. 伺服器端 **採集結算 API**（輸入：節點 id、身分；輸出：材料物件（`source_class` + `source_node_id`）＋敘事鍵；**不含**品階——品階在剝名時定，成數在提出時定），與現有 `Gather`／背包接口對接。  
3. NPC `Gather` 意圖改為指向 **真實節點 id**（取代同類房間標籤快閃）。  
4. 編輯器或腳本 **可視化摆点**（hex 上標記節點）。
