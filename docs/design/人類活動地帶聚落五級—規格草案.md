## 零、總綱（對談定案）

**先保證世界觀物理正確，再追求地圖多樣性。** 不符合硬約束的結果，漂亮也要丟掉。

**一句話（玩家觸發 × 系統分段）**：玩家觸發決定世界走向；系統**分段**完成世界細節——對應「觸發式預展開」，不是「觸發式一次全決定」。

## 一、聚落門檻（彼此相鄰 + 聯外交通）

以下為 **Tanger G 原文結構**；表內數字與之一致。

- **村**：彼此相鄰的 **（5 功能 + 10 民宅）** + **1** 條聯外道路。  
- **鎮**：彼此相鄰的 **（10 功能 + 30 民宅）** + **2** 條接通 **村級** 的道路。  
- **市**：彼此相鄰的 **（15 功能 + 40 民宅）** + **3** 條接通 **村級** 的道路，**或** **2** 條道路 + **1** 條接通 **鎮級** 的水路。  
- **府**：彼此相鄰的 **（25 功能 + 80 民宅）** + **4** 條接通 **鎮／市級** 的道路，**或** **3** 條道路 + **1** 條接通 **市級** 的水路。  
- **都**：彼此相鄰的 **（40 功能 + 150 民宅）** + **6** 條對外幹線（**至少 4** 條道路；其餘可為接通 **市／府級** 的水路）。

### 主表（速查）

| 級別 | 功能格 | 民宅格 | 聯外條件 |
|------|--------|--------|----------|
| **村** | 5 | 10 | **1** 條聯外道 |
| **鎮** | 10 | 30 | **2** 條接通村級道路 |
| **市** | 15 | 40 | **3** 條村級道路 **或** **2** 道 + **1** 鎮級水路 |
| **府** | 25 | 80 | **4** 條鎮／市級道路 **或** **3** 道 + **1** 市級水路 |
| **都** | 40 | 150 | **6** 幹線（道路 **≥4**，其餘可市／府級水路） |

### 1.1 聯外通道：官方暢行 vs 捷徑（定案）

- 表內「聯外道／幹線／水路」僅指 **遊戲內官方視角下暢行無阻** 的聯外通道：常態可通行、可作 **治理／稅務／公文／正規商旅** 所認可的幹線，**不**含「能走但風險明顯較高」的路徑。  
- **捷徑**（密道、未整備隘口、盜匪常走山徑、`portal` 類傳送／捷徑、季節性險路等）：**拓撲上或可連通**，供玩法、事件、玩家自選路徑；**不計入** §一 條數，也 **不進** `count_outbound_links` 的官方幹線統計。  
- 捷徑 **升格為官方幹線**：須經建設／驛站化／撤卡等 **明確流程**，在資料層標為 **官方邊**（見 §12.4、`link_class`，§16.2）並通過驗證後，始納入 §一。

## 二、下級依附門檻

| 級別 | 依附條件 |
|------|----------|
| **村** | 無 |
| **鎮** | 至少 **2** 個 **村** 依附 |
| **市** | 至少 **2** 個 **鎮** 依附，且總依附 **村** 數 **≥ 4** |
| **府** | 至少 **2** 個 **市** 依附，且總依附 **鎮** 數 **≥ 4** |
| **都** | 至少 **2** 個 **府** 依附，且總依附 **市** 數 **≥ 4** |

### 依附的判定（定案：圖論可達，似物理）

- **只採一種語意**：**官方聯外子圖**（§1.1、§12.4）上的可達性（圖論）。某下級聚落「依附於」上級，若且唯若在**當前世界狀態**下，兩者之間存在 **僅由官方邊構成**的道路或水路連通路徑（與 §一 所計幹線同一套邊；**不含**捷徑／高風險可通邊）。  
- **不採**：純空間半徑（未連通卻算依附）、以宏區劃界代替可達。  
- **路斷、橋毀、水陸中斷** → 該條依附關係 **立即不成立** → 觸發 §三 **降級**檢核；**不給**「系統日曆緩衝／假裝仍依附」。  
- **恢復**：須靠 **遊戲內** 修路、修渡口、清障、任務或建設等行為，使拓撲再度可達後，才可能重新滿足門檻（是否自動升級另表，預設不降不升只檢核）。  
- **檢核時機（定案方向）**：**拓撲變更時**重算依附（通／斷路、新格揭露改變連通、設施毀損等）；不必為此發明與物理無關的寬限。

## 三、降級規則

- **交通／依附** 不滿足 → 聚落 **自動降一階**，不允許硬掛高級稱號。  
- 與區域規則中「交通不達標或依附不達標，聚落自動降級」一致。

## 四、區域規則 v0.1（硬限制草案）

### 4.1 全域（所有區域）

- 探索後格子 **永久釘死**，不重骰。  
- **先地形、後設施**；設施不得覆寫地形硬阻擋語義。  
- **山脈不可貫穿**；洞口只可邊緣進入，不可打通對側。  
- **城牆必有城門**；城防必形成 **閉環**（純牆或混合自然屏障）。  
- **交通不達標或依附不達標** → 聚落自動降級。

### 4.2 村域（Village Core）

**禁止**：無城門而有城牆；出現 **都／府** 級機構（高階治理核）；功能格與民宅 **完全隔離** 成兩塊不連通。  
**必備**：至少 **1** 條聯外道路；村級最小格組 **5 功能 + 10 民宅**；至少 **1** 個生活補給點（**井／糧／簡易市集** 其一）。

### 4.3 鎮域（Town Core）

**禁止**：少於 **2** 條接通村級道路；僅有功能區無民宅群；所有道路 **只內循環**、無對外出口。  
**必備**：鎮級最小格組 **10 功能 + 30 民宅**；至少依附 **2 村**；至少 **1** 個公共核心（**市集／公所／衛所** 擇一）。

### 4.4 市域（City Core）

**禁止**：交通不滿足（**3** 道路或 **2** 道路 **+1** 水路）；**直接貼邊惡地無緩衝**；城防存在但 **無合法城門連通**。  
**必備**：市級最小格組 **15 功能 + 40 民宅**；至少依附 **2 鎮**（且累計 **≥4 村**）；至少 **1** 組城防閉環（純牆或混合閉環）。

### 4.5 府域（Prefecture Core）

**禁止**：低於 **4** 條對外幹路（或 **3** 路 **+1** 市級水路）；**缺次級節點**（只有中心沒衛星）；治理中心與物流中心 **完全斷連**。  
**必備**：**25 功能 + 80 民宅**；至少依附 **2 市**（累計 **≥4 鎮**）；至少 **1** 個區域級轉運點（陸或水）。

### 4.6 都域（Capital Core）

**禁止**：對外幹線不足（至少 **6**，且道路 **≥4**）；**無多層防線**（只有單圈薄防線）；與下級聚落 **脫鉤**（空心首都）。  
**必備**：**40 功能 + 150 民宅**；至少依附 **2 府**（累計 **≥4 市**）；至少 **1** 組主城防 **+1** 組次城防（可混合自然邊界）。

### 4.7 郊農帶（Agri Fringe）

**禁止**：大量重工／高危設施貼農田核心；農帶 **無灌溉或無道路** 接入；全農 **無聚落節點**（無人活動）。  
**必備**：農田與農舍 **同時存在**；至少 **1** 條連往村／鎮道路；至少 **1** 個糧儲節點（糧倉／集散點）。

### 4.8 山緣採掘帶（Mountain Edge Extraction）

**禁止**：洞口生在 **非山脈邊緣**；坑道觸達山脈 **對側邊界**；山脈核心被改為 **可通行**。  
**必備**：洞口格（礦洞／山洞）必連可進入坑道；坑道深度 **受上限**；至少 **1** 條回到人類活動帶的補給路。

### 4.9 水岸港埠帶（River/Lake Port Fringe）

**禁止**：碼頭生在 **非臨水格**；只有水路 **無陸路** 接駁；水陸交會點被牆體 **完全封死且無門**。  
**必備**：至少 **1** 個合法靠泊點（Dock）；至少 **1** 條接通鎮／市級陸路；若作城防邊界，需滿足 **「水域—牆—門—牆—水域」** 閉環語義。

## 五、生成流程 v0.2（固定順序）

1. **外框生成** — 山脈、水域、城牆、城門、聯外幹線先定。  
2. **區域分型** — 村／鎮／市／府／都 + 郊農帶 + 山緣採掘帶 + 水岸港埠帶。  
3. **硬約束檢核 A（拓撲）** — 閉環、可達、不可貫穿、門合法、交通最低線。  
4. **設施投放（配額）** — 先必備，再可選。  
5. **硬約束檢核 B（區域）** — 每區 **3 禁止／3 必備** 逐條驗證。  
6. **探索揭露層** — 未探索僅未知；首次探索才實例化細節並落盤。  
7. **落盤鎖定** — 成功即釘死；後續只允許事件覆寫，不重骰。

### 三道防呆閘

- **Gate-1 拓撲閘**：外框不合法 → 重生外框。  
- **Gate-2 區域閘**：分型不合法 → 先局部修補；失敗才回退。  
- **Gate-3 聚落閘**：依附／交通不足 → **自動降級**，不硬升級。

### 三份表（落地後機率怎麼調都不失真）

- **表 A**：不可違反規則（hard constraints）  
- **表 B**：區域必備／禁止（zonal）  
- **表 C**：聚落等級門檻（功能格、民宅、道／水路、依附）

## 六、探索生成 v0.3（驗收／回退／追錯）

### A) 最小驗收指標（10 條，全過）

1. 一次生成、永久釘死：同一格首次生成後不得被重骰覆寫。  
2. 山脈零貫穿：不得存在從山一側穿到另一側的可通行鏈。  
3. 洞口合法：入口在山脈邊緣，且連有效坑道。  
4. 城牆必有門：任一城牆閉環至少 **1** 門，且門為有效通道。  
5. 城防閉環成立（純牆或混合）。  
6. 聚落不空心：鎮／市／府／都依附未達 → 一律降級。  
7. 交通達標：各級道／水路最低線必達。  
8. 區域必備齊全：每區 **3 必備** 全滿足。  
9. 區域禁制零違反：每區 **3 禁止** 全不觸發。  
10. 探索可達性：玩家當前可達域內至少 **1** 條合法擴展路徑（避免卡死）。

### B) 失敗回退（由小到大）

| 層級 | 行為 |
|------|------|
| **L1** | 局部重投：單格／單設施違規，只重投該格或半徑 **r=2** |
| **L2** | 區塊回滾：同區連續 **N1** 次失敗（建議 **5**）→ 整區重生 |
| **L3** | 外框重生：拓撲硬錯連續 **N2** 次（建議 **3**）→ 回到外框階段 |
| **L4** | 保底降級：條件始終不達標 → 不再硬試，**降級並落盤**（防卡死） |

### C) Debug 欄位（每次生成／重試）

`seed`、`chunk_id`、`phase`（外框／分型／設施／檢核）、`rule_id`、`failure_cells`、`retry_level`（L1–L4）、`retry_count`、`final_resolution`。

### D) 暫定常數

- **N1 = 5**（區塊內局部重投上限）  
- **N2 = 3**（外框重生上限）  
- 探索擴展保底：**當前可達域至少 1 條新擴展**

## 七、嚴苛回退 vs 保底（對談定案）

- **硬約束**（違反＝世界壞掉）→ 可嚴苛。  
- **理想成果**（湖要大、坑道要豐富）→ 應 **縮水**，不是 **歸零**。  
- 每種觸發須有 **最小合法解（FallbackMin）**：`結果 = Clamp(理想, 硬約束)`，再不行 → `FallbackMin(觸發類型)`，保證 **非空**、可敘事、可擴展。

**全域多樣性**：單山可無礦坑；**全世界**不可永遠無礦——見 Hex 草案配額／欠帳。

## 八、觸發規格 v0.1（討論稿）

**全域**：每次觸發最多 **1 主結果 + 1 副結果**；先做**外框骨架**，細節進**背景佇列**；黑格仍由玩家慢慢開；必經硬約束檢核，失敗回退不硬塞。

### 8.1 `road` 觸發

| 欄位 | 定義 |
|------|------|
| **輸入** | 玩家首次揭露為 road 的格；當前可達域、附近已知聚落等級 |
| **主輸出** | 最近合法人類活動節點之 **聚落骨架**（村／鎮／市其一） |
| **副輸出** | 補一段連接骨架（道路或既有道路加粗段） |
| **硬限制** | 不違反聚落交通門檻；不空心；不穿越山脈硬阻擋 |
| **回退** | A) 降級聚落（市→鎮→村） B) 仍不合法則只保留道路、不生聚落 |

### 8.2 `water`／`river` 觸發

| 欄位 | 定義 |
|------|------|
| **輸入** | 首次揭露 water 或 river；鄰近水網、地勢語義 |
| **主輸出** | 水體骨架：**河段延展／湖泊邊界／海岸邊界**（擇一） |
| **副輸出** | 可選：沿岸節點（碼頭雛形或水岸聚落骨架） |
| **硬限制** | 河流連續；湖海不可孤立單格奇點；碼頭臨水且可接陸 |
| **回退** | A) 純水體骨架、不生沿岸節點 B) 水網衝突則縮小半徑重試一次 |

**資料語意**：**河流格** 與 **湖泊／海洋（水域格）** 分開；玩家骰出何類，後台在附近生成對應水體或聚落（與兩段式生成對齊）。

### 8.3 `mountain` 觸發

| 欄位 | 定義 |
|------|------|
| **輸入** | 首次揭露 mountain；鄰近山體、邊緣判定 |
| **主輸出** | 山體外框骨架 + 合法入口（山洞／礦洞） |
| **副輸出** | 背景佇列：坑道細節（主脈先行） |
| **硬限制** | 不可貫穿；入口僅邊緣；坑道不可觸達對側邊界 |
| **回退** | A) 保留山體、取消入口 B) 入口改位一次；再失敗則不生入口 |

### 8.4 觸發後驗證（每次）

`topology_ok`、`zonal_ok`、`settlement_ok`、`freeze_ok`（已探索格未被覆寫）。

### 8.5 兩段式（對 Tanger「後台一次生成、玩家慢慢開黑格」的修正）

- **段 A**：立刻生成 **外框骨架**（可感知延遲低）。  
- **段 B**：**異步**補全聚落內功能格、坑道支脈、岸線細節。  
- 避免：連鎖爆生、拓撲打架、計算尖峰；語意仍為「觸發式預展開」。

## 九、聚落內部佈局生成規格 v0.1（對談定案 2026-04-09）

> **定位**：§五「設施投放（配額）」的展開。本節定義**同一組 F+R 格如何在 Hex 地圖上空間展開**——從道路骨架到功能格、住宅、防禦閉環、邊緣帶的逐層放置公式。  
> **前提**：§一門檻已決定 F+R 數量與聯外條件；§四區域規則為硬限制。本節產出須通過 §六 驗收。

### 9.1 生成原則

1. **道路驅動生長**：聚落形狀由道路骨架決定，不是先畫圓再填格。  
2. **三層放置**：道路 → 功能格（沿路） → 住宅（填充）。  
3. **天然屏障優先**：城防先掃描周圍自然地形（山脈、水域），城牆僅補缺口。  
4. **種子確定性**：同 `seed` + 同 `tier` + 同地形上下文 = 同佈局。  
5. **最小合法解**：寧可縮水（少生幾格住宅）也不違反 §四 硬約束。

### 9.2 道路骨架生成

**輸入**：聯外道路方向（§一條數）、`anchor_cell_id`（錨格）、周圍地形。

**步驟**：

1. 每條聯外道路從聚落邊界向中心延伸，匯聚於 **錨格**（或錨格附近的十字路口格）。  
2. 道路格數不計入 F 或 R 配額——純基礎設施。  
3. 多條道路交匯時，優先形成 **十字** 或 **丁字** 路口（axial 座標六向取交角最大的組合）。  
4. 道路段長度由 `seed` 擲骰，範圍 `[3, tier_radius]`；`tier_radius` 見 §9.8。

| 級別 | 道路數 | 典型骨架形狀 |
|------|--------|-------------|
| 村 | 1 | 直線進入 |
| 鎮 | 2 | 十字或丁字 |
| 市 | 2~3 | 十字 + 斜街 |
| 府 | 3~4 | 多軸放射 |
| 都 | 4~6 | 放射 + 環路 |

### 9.3 功能格放置

**規則**：功能格必須 **鄰接道路格**（六向至少一格為道路）。

**放置順序**：

1. **錨點**：第一個功能格為 **市集（market）**，放在錨格或錨格的道路鄰格。  
2. **核心功能**：從功能格池（§9.5）依優先序取出，沿道路兩側交替放置，優先填十字路口四角。  
3. **次要功能**：核心填滿後，向道路延伸方向繼續放置。  
4. **禁止**：兩個同類型功能格相鄰（seed 碰撞時重擲位置）。

### 9.4 住宅格放置

**規則**：住宅格必須 **鄰接至少一個已放置的格**（功能格、道路或其他住宅），形成連通群。

**放置順序**：

1. **核心住宅**：緊鄰功能格的空位，優先填充。數量約 `R × 0.4`。  
2. **填充住宅**：從核心住宅向外擴散（BFS），每次取離道路最近的空鄰位。數量約 `R × 0.4`。  
3. **邊緣住宅**：剩餘配額填在最外圈，形成不規則邊界（不要整齊圓形）。數量約 `R × 0.2`。  
4. **有機偏移**：每格放置時，以 `seed` 對 6 方向加權擲骰，製造不對稱形狀。

### 9.5 功能格類型池

每級 **必備** 格從上一級繼承並擴充。`seed` 從 **可選** 池中補滿配額。

| 級別 | 必備 | 可選池（seed 抽取補滿） |
|------|------|------------------------|
| **村** (5F) | market, inn, blacksmith | general_store, clinic, workshop, farmhouse, granary |
| **鎮** (10F) | 村必備 + tavern, general_store | clinic, stables, temple, workshop, warehouse, granary, guard_post |
| **市** (15F) | 鎮必備 + clinic, guard_post, town_hall | guild_hall, library, barracks, stables, dock, bathhouse, temple, warehouse, academy |
| **府** (25F) | 市必備 + barracks, courthouse, bank | jail, mint, academy, arena, library, bathhouse, embassy, observatory, warehouse, dock, stables, caravanserai |
| **都** (40F) | 府必備 + academy, mint, arena | theater, observatory, alchemist, mage_tower, embassy, prison_yard, caravanserai, guild_hall（可重複不同名） |

**重複規則**：同一類型可出現多次（如大城有多個 warehouse），但須 **不相鄰** 且各帶不同 `name`。

### 9.6 防禦閉環生成（市級以上）

**觸發**：§四.4 市域起要求至少 1 組城防閉環。

**步驟**：

1. **計算聚落凸包**：對所有已放置的格（道路+功能+住宅），取外圈鄰格集合作為 **候選城防線**。  
2. **掃描天然屏障**：候選線上若鄰接 `mountain` 或 `water`/`water_deep`，標記為 **天然段**，不放城牆。  
3. **填補城牆**：天然段之間的缺口，以 `wall` 格填補，形成閉環。  
4. **城門**：每條道路穿越城防線處，該格 **不放牆**，保留道路（即城門）。城門格不額外佔 F 配額。  
5. **驗證閉環**：從任一城外格 BFS，不得能繞過城防線進入城內（不經城門或天然屏障）。  
6. **都級雙層**：§四.6 要求主城防+次城防。內圈為核心城防，外圈含郊區的次城防（可較稀疏，混合天然）。

**混合閉環範例**：

```
山山山山山        ← 天然（北）
牆        牆      ← 人工（東西）
牆  [城區]  牆
牆        牆
門  道路  門      ← 城門（南，道路穿越處）
水水橋水水水      ← 天然+橋門（南）
```

### 9.7 邊緣帶生成

聚落外圍可附加邊緣帶（不計入 F+R 核心配額，但歸屬同一 `settlement_id`）。

| 邊緣帶 | 觸發條件 | 格組成 | 放置規則 |
|--------|---------|--------|---------|
| **郊農帶** | 所有聚落（§4.7） | farm_field + farmhouse + granary | 沿非城防側外延 1~3 格深，需道路接入 |
| **山緣採掘帶** | 聚落鄰接山脈（§4.8） | 礦洞入口格 + 坑道（另表） | 洞口在山脈邊緣，連補給路 |
| **水岸港埠帶** | 聚落鄰接水域（§4.9） | dock + warehouse | 碼頭臨水，陸路接駁 |

### 9.8 聚落空間半徑（參考值）

從錨格到最外圈住宅的 hex 距離上限。超出則 BFS 放置跳過該位。

| 級別 | `tier_radius`（格） | 含防禦+邊緣帶總直徑估 |
|------|---------------------|----------------------|
| 村 | 3 | ~7 格寬 |
| 鎮 | 5 | ~11 格寬 |
| 市 | 7 | ~15 格寬（含城牆） |
| 府 | 10 | ~21 格寬 |
| 都 | 14 | ~29 格寬（含雙層城防） |

### 9.9 生成偽碼（概覽）

```
fn generate_settlement_layout(seed, tier, anchor, terrain_context) -> Vec<HexCell> {
    let rng = seed_rng(seed);

    // 1. 道路骨架
    let roads = generate_road_skeleton(rng, tier, anchor, terrain_context.external_dirs);

    // 2. 功能格
    let mut pool = functional_pool(tier);
    let facilities = place_functional_cells(rng, &roads, &mut pool, tier.f_count);

    // 3. 住宅
    let residentials = place_residential_cells(rng, &roads, &facilities, tier.r_count, tier.radius);

    // 4. 城防（市+）
    let defenses = if tier >= City {
        generate_defense_ring(&roads, &facilities, &residentials, terrain_context)
    } else { vec![] };

    // 5. 邊緣帶
    let fringes = generate_fringes(rng, tier, &roads, terrain_context);

    // 6. 驗證 §四 + §六
    let all_cells = [roads, facilities, residentials, defenses, fringes].concat();
    validate_or_fallback(all_cells, tier)
}
```

## 十、v0.4 資料契約與檢核介面（草案，准擬）

> 語言無關；欄位名用 **snake_case** 方便對齊 Rust／JSON。座標型別對應專案 Hex（axial `q,r` 或內部 id）。

### 10.1 `SettlementRecord`（聚落實體）

| 欄位 | 型別（概念） | 說明 |
|------|----------------|------|
| `settlement_id` | UUID | 穩定主鍵 |
| `tier` | 枚舉 `village`…`capital` | **目標／宣稱**等級（生成意圖） |
| `effective_tier` | 同上 | **上次檢核後**實際等級（可低於 `tier`） |
| `chunk_id` | 字串 | 所屬宏區／玩家區（除錯、存檔分片） |
| `facility_cell_ids` | 有序 id 列表 | 功能格集合（與 §一 計數一致） |
| `residential_cell_ids` | 有序 id 列表 | 民宅格集合 |
| `anchor_cell_id` | id | 代表格（城門／中心參考，檢核與敘事用） |
| `zone_type` | 枚舉 | `village_core`…`port_fringe` 等，對應 §四 |
| `dependency_peer_ids` | `settlement_id` 列表 | 宣稱依附的**下級**聚落（邏輯層） |
| `last_topology_hash` | 字串／u64 | 上次通過依附檢核時的拓撲指紋（見 §10.3） |

依附是否仍成立**不**靠快取信任：`dependency_peer_ids` 僅為候選；每次檢核在當前圖上 **重算可達**（見 §二 依附定案）。

### 10.2 `TransportEdge`（聯外邊，圖論邊）

| 欄位 | 說明 |
|------|------|
| `edge_id` | UUID |
| `endpoint_a` | `settlement_id` **或** 邊界格 id（實作擇一，但要能還原「接到哪一聚落」） |
| `endpoint_b` | 同上 |
| `mode` | `road` \| `water` |
| `operational` | bool；`false` ＝路斷／渡口失效，該邊不參與可達 |

聚落「幾條聯外道接到村級」等 §一 條件，改為在 **operational 邊子圖** 上計數／驗證。

### 10.3 `topology_hash`（拓撲指紋）

對「所有 `operational` 交通邊 + 與聚落相關之可步行格（或 BFS 閉包）」做**規範化排序**後哈希。  
**任何**邊增刪、`operational` 翻轉、影響連通之格契約變更 → 哈希變 → 觸發 **依附／交通重算** 與 **Gate-3**。

### 10.4 `ValidationReport`（單次檢核結果）

| 欄位 | 說明 |
|------|------|
| `subject_id` | `settlement_id` 或 `chunk_id` 或 `edge_id` |
| `ok` | bool |
| `gate` | `topology` \| `zonal` \| `settlement` |
| `rule_id` | 失敗時：對應表 A／B／C 或 §四／§六 條目代碼 |
| `failure_cells` | 可選，違規格 id 列表 |
| `retry_level` | `L1`…`L4`（對齊 §六 B） |
| `resolution` | `pass` \| `patch` \| `rollback_block` \| `regenerate_frame` \| `downgrade_applied` |

### 10.5 檢核函式介面（偽簽名）

```
build_transport_graph(world, visibility: public|authoritative, link_layer: official|exploration) -> Graph
  // visibility：§12.2（契約揭露 vs 全量）。link_layer：§12.4（官方聯外 vs 併入捷徑／portal）。
  // 依附、§一 計數、Gate-3：visibility=authoritative 且 link_layer=official。

reachable(a_settlement_id, b_settlement_id, graph) -> bool
  // graph 應為 official 子圖（§二）。

count_outbound_links(settlement_id, graph, target_tier_min, mode_filter) -> counts
  // graph 應為 official；實作 §一「接到村／鎮／市…」之官方幹線計數

validate_gate_topology(world) -> Vec<ValidationReport>
validate_gate_zones(world) -> Vec<ValidationReport>
validate_gate_settlements(world) -> Vec<ValidationReport>
  // 內含：依附僅承認 official 子圖上之 reachable；再比對 §一～§三、§四

on_topology_changed(world, changed_cell_or_edge_ids) -> void
  // 重算 topology_hash、對受影響 settlement 跑 validate_gate_settlements、套用降級
```

**升級**：本草案預設 **不**自動升級；`tier` 可由事件／建設流程提交，再跑全套檢核通過後才寫入 `effective_tier`（細節可另表）。

## 十一、`road` 觸發 → 聚落骨架等級（決策表 v0.1，准擬）

**輸入**：`anchor_cell_id`、當前 `build_transport_graph(..., authoritative, official)` 子圖、`seed`、錨點 **hop 距離內**已知 `effective_tier` 的鄰聚落集合。

**步驟**（由高到低試骨架；與 §八 1 主 + 1 副、FallbackMin 一致）：

1. 依種子與鄰域供需，**候選目標** `target_tier` ∈ `{ city, town, village }`（府／都**不**由單次道路首觸發直接骨架化，避免爆量）。  
2. 以 `target_tier = city` 組 **15／40 + §一 市級交通** 骨架（僅外框 + 最小設施錨點）；跑 `validate_gate_settlements` + `validate_gate_zones`。  
3. 失敗 → `target_tier = town`（10／30 + 鎮級交通）→ 再驗證。  
4. 再失敗 → `target_tier = village`（5／10 + 1 聯外）→ 再驗證。  
5. 仍失敗 → **副結果作廢**，主結果降為：**僅延伸道路骨架**（FallbackMin），**不**生成聚落實體；`ValidationReport.resolution = patch` 或對應 L1。

**依附**：新生聚落若宣稱依附，**同一輪**僅允許連到 **已存在且 reachable** 之下級節點；若數量不足，骨架等級須下調或改為無依附之村（再驗證）。

## 十二、v0.4 補遺（預設決案，可改）

### 12.1 `TransportEdge` 端點怎麼存

- **常態**：`endpoint_a` / `endpoint_b` 存 **`settlement_id`**（依附與 §一 計道數最直）。  
- **過渡**：聚落尚未掛牌前，可暫存 **格 id**；`SettlementRecord` 落盤後 **遷移** 為雙端 `settlement_id`，並保留 `anchor_cell_id` 供除錯。  
- **不採**：長期只存格、不解析屬於哪個聚落（會讓 Gate-3 與依附難寫）。

### 12.2 `topology_hash`：兩條指紋

| 名稱 | 納入範圍 | 用途 |
|------|-----------|------|
| `topology_hash_public` | **僅**玩家已揭露（契約層）之格＋對其可見之 operational 邊 | UI、客戶端預測、防作弊比對（可選） |
| `topology_hash_authoritative` | **伺服器已提交**之全部格與邊（含未揭露但已落盤之骨架、後台段 B 補全） | **依附**、**降級**、**Gate-1～3** |

**定案**：依附與交通門檻以 **`authoritative`** 為準——後台已生成的路／水只要已落盤，路斷即斷、路通即通；**不**因「玩家還沒開霧」假裝沒路。敘事仍只顯示黑格，屬體驗層，不騙模擬層。

### 12.3 修路／開渡口 → 寫邊

- **事件入口**：`apply_transport_change(Action)`，`Action` ∈ `{ OpenEdge, CloseEdge, RepairEdge, BuildBridge, … }`。  
- **效果**：新增或更新 `TransportEdge`（`operational := true`）、或標 `false`；呼叫 `on_topology_changed`。  
- **升級 `effective_tier`**：僅在 `validate_gate_settlements` **全通過**後，由明確流程（非每 tick 自動）寫入。

### 12.4 官方聯外子圖 vs 全連通探索圖（定案）

| 圖 | 邊的組成 | 用途 |
|----|-----------|------|
| **官方聯外子圖** | 滿足 `can_walk`（或合法水路）之鄰接步 **且** 標為 **`link_class: official`** 之 `transport_edges`；**可選**納入經標記為官方幹線之 `portal`（預設 **不**） | §一 計數、`count_outbound_links`、**§二 依附**、降級檢核 |
| **探索／玩法圖** | 上列 **併入** 未標官方之 `portal`、捷徑邊、高風險可通邊 | 尋路選項、事件、玩家「抄近路」、戰鬥撤退 |

**預設**：新建 `portal`、未標類別之邊 → **不**進官方子圖。`HexGrid::find_path` 類 BFS 若服務「能不能偷渡到」可用探索圖；**Gate 與依附** 僅用官方子圖。

## 十三、`water`／`river`、`mountain` 觸發決策（v0.1，准擬）

與 §八 相同：**1 主 + 1 副**；先骨架後背景；失敗走 §八回退欄。

### 13.1 `water`／`river`

**主輸出試序**（由高結構到低）：`coast_or_lake_shell` → `river_extension` → `minimal_water_kernel`（單段連續水體或最小湖核，FallbackMin）。

**副輸出**：沿岸 `Dock` 錨格 **或** 水岸聚落骨架（僅當主輸出已合法且配額允許）。

**驗證順序**：`topology_ok`（水體連續、無單格湖海奇點）→ `zonal_ok`（§4.9）→ `settlement_ok`（若有副聚落骨架）。

### 13.2 `mountain`

**主輸出試序**：`ridge_shell + legal_entrance` → `ridge_shell_only`（FallbackMin：山體外框，**無洞**）。

**副輸出**：背景佇列坑道網（主脈）；不得觸發對側邊界。

**驗證順序**：貫穿檢 → 入口臨邊 → `zonal_ok`（§4.8）。

## 十五、`rule_id` 編碼與 `Action` 權限（v0.1，可實作）

與 §十四 前綴一致；本節給 **字串形狀** 與 **誰能改拓撲**，供 log／telemetry／後台審計共用。

### 15.1 `rule_id` 細粒度編碼

**形狀**（建議，全小寫＋連字號，避免與版本號混淆故**不**用點號分段）：

| 段 | 取值 | 說明 |

**範例**（非窮舉，實作可擴表）：

| `a-global-mountain-through` | §4.1 山脈貫穿 |
| `a-global-wall-no-gate` | §4.1 城牆無門 |
| `a-global-edge-geometry-mismatch` | §16.3.1 顯式邊與 `can_walk`／屏障矛盾 |
| `b-village-wall-no-gate` | §4.2 村域禁止 |
| `b-town-link-road-insufficient` | §4.3 鎮域道路條件 |
| `b-city-buffer-badlands` | §4.4 市域貼邊惡地 |
| `c-tier-residential-count` | §一 民宅／功能格數不足 |
| `c-tier-link-road-count` | §一 聯外道路／幹線計數失敗 |
| `c-tier-link-water-count` | §一 水路幹線計數失敗 |
| `c-dep-lower-count` | §二 依附數量不足 |
| `c-dep-reachable` | §二 圖論不可達（依附斷） |

**單一 `rule_id` 長度**：建議 **≤ 64 UTF-8 位元組**（含前綴），便於 DB 欄位與索引；超長改縮寫表另開對照。**單次 `ValidationReport`** 內 `rule_id` 列表建議 **≤ 32 筆**；更多則合併為 `a-global-batch` 類摘要＋附檔詳表。

**`failure_cells`**：值為格 id 字串；單次回報建議 **≤ 256 格**，避免 payload 膨脹。

### 15.2 `Action` 列舉（拓撲寫邊）

與 §12.3 銜接；名稱為 **邏輯動作**，實作可對應一或多個 `TransportEdge` 變更。

| `Action` | 效果（摘要） |
|----------|----------------|
| `OpenEdge` | 新增或啟用一條邊（`operational := true`）。 |
| `CloseEdge` | 停用或移除可通行語意（戰爭／塌方／人為封路）。 |
| `RepairEdge` | 將既有邊自不可用恢復為可用（不必然改幾何）。 |
| `BuildBridge` | 跨越水域／裂谷等，建立 **道路類** 邊（仍受地形／區域規則檢核）。 |
| `DemolishBridge` | 拆除橋梁 → 等同 `CloseEdge` 或刪邊，觸發 `on_topology_changed`。 |
| `OpenFerry` | 開設／恢復 **渡口**（水路邊，與 `BuildBridge` 分帳以利統計與敘事）。 |
| `CloseFerry` | 關閉渡口。 |
| `SetEdgeWeight` | 調整 **旅行成本**（見 §15.5）；**不**改連通性、**不**以 `weight=∞` 冒充斷邊。 |

**未列舉之設施**（隧道口、城門開關）：若語意上等價於邊的啟停，**映射**為上表之一並在 payload 註 `facility_kind`。

### 15.3 行為者（`ActorKind`）與預設權限矩陣（v0.1）

**行為者**：

| `ActorKind` | 說明 |
|-------------|------|
| `system_generator` | 後台分段生成、Parser、補全骨架 B；**唯一**可在未揭露格上寫入 authoritative 拓撲（仍須通過區域／門檻檢核）。 |
| `world_event` | 天災、戰事、劇情轟城等批次改世界狀態。 |
| `npc_faction` | 有領地／工單的 NPC 或派系（修路隊、守軍）。 |
| `player` | 玩家透過營建、任務獎勵、消耗資源的互動。 |

**預設權限**（可藉世界狀態／標籤覆寫；**空白＝預設不允許**）：

| `Action` | `system_generator` | `world_event` | `npc_faction` | `player` |
|----------|:------------------:|:-------------:|:-------------:|:--------:|
| `OpenEdge` | ✓ | ✓（劇情／事件表） | ✓（須有工單／領地範圍內） | ✓（須滿足玩法解鎖與資源） |
| `CloseEdge` | ✓ | ✓ | ✓（守軍／破壞任務） | 通常 ✗（特例：玩家陷阱／合法拆除另表） |
| `RepairEdge` | ✓ | ✓ | ✓ | ✓ |
| `BuildBridge` | ✓ | 視事件 | ✓ | ✓ |
| `DemolishBridge` | ✓ | ✓ | ✓ | 通常 ✗ |
| `OpenFerry`／`CloseFerry` | ✓ | ✓ | ✓（港埠設施） | ✓（須臨水格＋許可） |
| `SetEdgeWeight` | ✓ | ✓ | ✓ | ✓（皆須伺服器上下限／反作弊；見 §15.5） |

**定案方向**：**誰能修路** 不是單選——**四類皆可**，差在 **伺服器對每一筆 `apply_transport_change` 做脈絡檢核**（範圍、劇情鎖、派系、資源、是否作弊）。`system_generator` 與玩家互動的邊界是：**已落盤即進 authoritative**，與 §12.2 一致；玩家不能只因「沒開霧」否定後台已生成的路。

### 15.4 現行 `data/hex/grid.json`／`HexGrid` 與概念對照（v0.1）

**現況**（`src/hex/grid.rs`）：地圖為 **`cells` 陣列** + **`barriers`**（`(coord, dir)` 單向擋）+ **`portals`**（非相鄰連通）。相鄰格之間 **無獨立 `TransportEdge` 列**；可步行與否由 **`can_walk`** 合成（目標格存在、地形 `walkable`、該向無 barrier、傳送門另計）。

| 本規格概念 | 現行 Rust／JSON 落點 | 備註 |
|------------|----------------------|------|
| 格 `cell_id` | `HexCell.coord`（`q`,`r`） | 正規字串見 [Hex格座標與cell_id規約](../reference/Hex格座標與cell_id規約.md)（預設 `{q},{r}` 無空白）。 |
| 相鄰 **道路邊**「關閉」 | `add_barrier`／`add_wall` 或把目標格改為不可走地形 | 對應 `CloseEdge` 的 **鄰接**語意。 |
| 相鄰邊「開啟」 | `remove_barrier`／`remove_wall` 或修正地形 | 對應 `OpenEdge`。 |
| **橋／幹線道路** | 常見為格上 `terrain` = `bridge`／`road` + 周邊水／崖之 barrier 語意 | 仍屬 **格＋屏障** 合成，非獨立邊表。 |
| **渡口／水路幹線**（§一 水路計數） | **尚未**有第一級欄位 | v0 可暫用 `Portal` + `HexCell.tags`／`zone` 標記 `ferry`／`water_route`，或次版新增 `transport_edges` 陣列與 `mode: road|water`。 |
| `settlement_id`、依附子圖 | **不在** `grid.json` | 另表（執行期／PG）；`build_transport_graph` 讀 **格＋屏障＋portal＋edge 擴充** 再掛聚落。 |
| **chunk 邊界** | **不在** 現行 schema | 屬 **載入／揭露** 索引：可另行在 cell 附帶 `chunk_id`、或獨立 chunk 索引檔；**不阻塞**拓撲語意。 |

**跨 chunk**：拓撲一致性的 **單一真實來源**仍是伺服器上的完整 `authoritative` 圖；chunk 僅影響客戶端載入與 `topology_hash_public` 子集，與 §12.2 一致。

### 15.5 `SetEdgeWeight`、Gate-3 與 §二 依附（定案）

採 **雙層語意**，避免與 `CloseEdge` 重複：

| 層級 | 用途 | 是否觸發 `on_topology_changed` |
|------|------|----------------------------------|
| **連通性（connectivity）** | §二 依附、Gate-3、§一「有無路／水路」 | **是**（邊啟停、屏障、不可走地形、刪 portal） |
| **旅行成本（travel cost）** | 尋路偏好、移動時間、季節／天氣敘事 | **否**（預設）；除非契約明訂「成本變更需重算某類快取」 |

**定案**：

1. **禁止**以「`weight = ∞` 但仍標為連通」充當斷路——實作上 **斷依附＝連通性斷**，應走 **`CloseEdge`、屏障、或不可走地形`**，與 §二「路斷即依附不成立」一致。  
2. **`SetEdgeWeight` 不參與** 依附與 Gate-3 的 **可達性**判定；僅影響 **帶權最短路／行程時間**（未來若在 `HexGrid` 加邊權，與現有 BFS 跳數可分軌）。  
3. 若玩法需要「泥濘季商隊極慢但村落仍算依附上級」，屬 **敘事與經濟層**，**不**改 §二 圖論可達結果。

### 15.6 收斂紀要

- **`cell_id`**：見 [Hex格座標與cell_id規約](../reference/Hex格座標與cell_id規約.md)（`v0.1`）。  
- **`TransportEdge` JSON 草案**：見 **§十六**；建議大世界 **分檔** `transport_edges.json`（或 PG 表），小工具可選 **併入** `grid.json` 頂層鍵 `transport_edges`。

## 十六、`TransportEdge` JSON 草案（v0.1）

與 §12.1、§15.4 一致；欄位名稱可隨實作微調，**語意**應保留。

### 16.1 端點（`Endpoint`）

聚落已掛牌：**`settlement_id`**；過渡期或幾何錨點：**`cell_id`**（格式見 cell_id 規約）。

```json
{ "settlement_id": "settlement_foo_01" }
```

```json
{ "cell_id": "12,-4" }
```

### 16.2 邊（`TransportEdge`）

| 欄位 | 型別 | 說明 |
|------|------|------|
| `id` | string | 可選；穩定主鍵，利於 log 與 diff。 |
| `endpoint_a` | Endpoint | 與 §12.1 雙端一致。 |
| `endpoint_b` | Endpoint | |
| `mode` | `"road"` \| `"water"` | 對應 §一 道路／水路幹線計數與敘事。 |
| `operational` | boolean | **連通性**；`false` 等同斷邊，觸發 `on_topology_changed`（§15.5）。 |
| `link_class` | `"official"` \| `"shortcut"` | 可選；**預設 `official`**。僅 **`official`** 進 §一 計數與 §二 依附子圖；`shortcut` 僅探索圖（§1.1、§12.4）。 |
| `weight` | number | 可選；**旅行成本**，預設 `1.0`；**不**單獨決定依附（§15.5）。 |

**範例**（陣列可獨立檔或嵌於 `grid.json`）：

```json
{
  "transport_edges": [
    {
      "id": "te-village-a-east",
      "endpoint_a": { "settlement_id": "set_village_a" },
      "endpoint_b": { "cell_id": "40,2" },
      "mode": "road",
      "operational": true,
      "link_class": "official",
      "weight": 1.0
    },
    {
      "id": "te-ferry-crossing",
      "endpoint_a": { "settlement_id": "set_town_m" },
      "endpoint_b": { "settlement_id": "set_village_n" },
      "mode": "water",
      "operational": true
    }
  ]
}
```

### 16.3 與 `HexGrid` 合成圖

`build_transport_graph(..., authoritative)` 的建議輸入：

1. **鄰接步行邊**：由 `cells` + `barriers` + 地形 `walkable` 導出（現行程式已有）；納入 **官方子圖** 時僅計可視為「暢行幹線」之格段（若某鄰接步屬險徑，須降為 `shortcut` 邊或拆出獨立 `transport_edges` 標記，見 §1.1）。  
2. **`portals`**：**預設不**進官方子圖；僅當 schema 明確 **`counts_as_official_link: true`**（或同等）且通過驗證時，才併入 §一／依附圖。其餘僅進探索圖。  
3. **`transport_edges`**：`operational` 且 `link_class: official`（或預設 official）者進官方子圖；`shortcut` 僅探索圖。  
4. **重載**：`build_transport_graph(..., scope: official | exploration)` —— **Gate／依附** 用 `official`；尋路 UI／AI「抄近路」可用 `exploration`（併入 2、3 之捷徑）。  

#### 16.3.1 連通性優先序（定案 v0.1）

- **單格鄰接之物理可走**：以 `HexGrid::can_walk`（地形 `walkable` ＋ `barriers`）為 **唯一真相**；**不**允許 `transport_edges` 宣告「穿牆／涉水無橋」之步兵連通。  
- **`transport_edges` 兩端皆為 `cell_id`** 時：若語意為「此幹線對應該鄰接步」，須與當下 `can_walk` **一致**；否則產出 **`ValidationReport`**（建議 `rule_id`：`a-global-edge-geometry-mismatch`），實作可 **拒絕提交** 或 **強制 `operational := false`** 直至修格／拆屏障。  
- **端點為 `settlement_id`** 的邊：圖上展開為聚落錨點格之間路徑時，路徑上每一鄰接步仍須滿足 `can_walk`（或契約另允許之 **水路 mode** 邊，見 §一）。  
- **冗餘**：同一對格既有合法 `can_walk` 又有語意重疊之 `transport_edges` → **不衝突**；幹線計數與敘事以 **邊之 `mode`／`id`** 去重，避免雙算（實作註記寫死去重鍵）。

### 16.4 UI／telemetry（v0.1 建議）

- 圖邊附可選 **`edge_source`**：`adjacency` \| `portal` \| `transport_edge`，利於篩選與除錯；`portals` 與 `mode: water` 之 `transport_edge` **可**同層繪製但以 **不同圖例** 區分（渡口≠地城傳送）。  
- 客戶端 **不必**把未揭露之 authoritative 邊畫出；與 §12.2 一致。

### 16.5 分片載入（v0.1 建議）

- 大圖採 **清單檔**（例 `hex_manifest.json`）：列出 `chunk_id` → `grid` 片段路徑、`transport_edges` 片段路徑（可空）。  
- **載入順序**：玩家 bbox（或鏡頭）優先，其次鄰 chunk；合併後再算 `topology_hash_authoritative` 子集快取。  
- 接軌當下兩區合併：見 **§十七** 與 [Hex探索揭露與漸進生成—規格草案](../reference/Hex探索揭露與漸進生成—規格草案.md) §七。

### 16.6 仍開（實作向）

- 多人同步、IOU 與決定性重播（見 Hex 探索 §八）。  
- `edge_source` 是否進持久化表或僅執行期派生。

## 十七、與 Hex 探索／野外分級之 hook（對照 v0.1）

供 [Hex探索揭露與漸進生成—規格草案](../reference/Hex探索揭露與漸進生成—規格草案.md) §七 **接軌**、§八 **未定案** 與 [野外大地圖區域與場所分級規格](野外大地圖區域與場所分級規格.md) 對表；**本檔**以村／鎮／市／府／都＋依附為主。野外 **Town／City** 與 Hex 聚落 **不同量綱**，但 **接軌完成後應同步收斂**（見 §17.1、下表）。

| 事件或語意（Hex／野外） | 本檔觸點 |
|-------------------------|----------|
| 兩區版圖 **接軌合併**、聯外圖合併 | `on_topology_changed`（§10.5）；重算依附與 `effective_tier`（§二、§三；Hex §七 末段） |
| 玩家只見黑格、後台已補路 | `topology_hash_public` vs `topology_hash_authoritative`（§12.2） |
| 道路首觸發／水體／山體生成 | §十一、§十三；回退 **FallbackMin** 對齊 Hex §五 |
| 幹線道路／水路是否計入 §一 | `build_transport_graph(..., authoritative, official)`；`transport_edges.mode` + `link_class: official`（§1.1、§12.4、§16） |
| 接軌後 **野外 Town／City** 與 **`effective_tier`** | **定案：同步**。同一輪接軌管線 **併行**跑野外 Node 規則與本檔 Gate；**不得**長期維持「野外 City、Hex 僅村級」等矛盾；若暫時不合，須 **阻擋接軌完成** 或 **同步降級／補骨架** 至一致。**數值映射**（擇一或階梯、Town→鎮下限等）仍可在本表增列，實作依表填寫。 |
| 野外 §5「每 Town **2** 外連 Node／City **3** 外連」 | **粗粒度 Node 圖**；與 §一 **官方**幹線 **不同層**，但接軌後須與聚落表現 **同向收斂**（非單向推論，見 §17.1） |

### 17.1 兩套「鎮／市」語意（釐清，定案）

| 軸 | 定義文件 | 空間單位 | 主要用途 |
|----|----------|----------|----------|
| **野外 Town／City** | [野外大地圖區域與場所分級規格](野外大地圖區域與場所分級規格.md) §1、§5～5.5 | Field Node、hop 距離 | 世界骨架、城際最短距離、節點類型配額 |
| **聚落 `effective_tier`** | 本檔 §一～§三、§十 | Hex 格、`build_transport_graph`（**official** 子圖） | 升降級、依附、區域規則 Gate |

**同步義務（定案）**：接軌合併寫入前，**野外檢核**與 **聚落檢核** **皆須通過**；通過後 **同批提交** 野外標籤與 `effective_tier`（及相關 Node／Hex 狀態），避免長期分裂。

**單向推論仍禁止**：不得僅由一軸結果 **覆寫** 另一軸；必須 **兩軸各自算完再對表**，不一致則修資料或阻擋提交——與「同步」相容（同步＝最終狀態一致，非「只改一邊」）。

**文件維護**：野外或 Hex 探索更新接軌段落時，應 **回看本節** 是否需增列映射列，避免雙檔漂移。
