## §零：為什麼推翻

639 格手刻花了無數個日夜。每一格要想名字、想描述、拉連線。
這不是設計，這是搬磚。設計者的腦應該花在世界觀，不是填表格。

現在有兩個成熟的開源生成器，輸出格式都是 GeoJSON / Full JSON，且已驗證可解析：

| 工具 | 職責 | 輸出品質 |
|------|------|----------|
| **Azgaar Fantasy Map Generator** | **世界骨架**（唯一來源）：大陸、國家、省、城鎮位置、路線、河流、地形、文化、宗教 | Full JSON 9MB，含 100 國 / 607 省 / 623 城鎮 / 4659 條歷史筆記，**鄰接拓撲現成** |
| **Watabou 全家桶** | **往下鑽**：城鎮內部、建築內部、野外地點 | 視覺優秀，需幾何推算拓撲 |

已選定地圖：**Celia**（seed: 938784876），設計者親手調過的完整世界。

Watabou 不負責世界地圖。Watabou 只在需要展開城鎮/地點內部時使用：

| 生成器 | 適用場景 |
|--------|---------|
| City | 大城市內部（首都、港口城） |
| Village | 小型聚落內部 |
| Cave/Glade | 野外資源點、林間空地 |
| Dungeon | 遺跡、危險地城 |
| Dwelling | 單棟建築內部（商店、旅店、工坊） |

**結論：不再手刻。Azgaar 出骨架 → Watabou 鑽細節 → Parser 轉格式 → 編輯器校對。**

## §二：Azgaar → 世界地圖（Parser A）

### 原始資料（已驗證：Celia Full JSON，9MB）

- **7691 個 Voronoi cell**，每格帶 `neighbors[]`（鄰接拓撲現成）
- **100 國**，每國帶 name、diplomacy、neighbors
- **607 省**，每省帶 name、fullName、burg（省會城鎮）
- **623 城鎮**（burgs），每座帶 name、x/y 座標、population、culture、state、citadel、plaza、port
- **14 文化 / 64 宗教 / 13 生態系**，全部有名字
- **504 路線**（53 公路 + 368 小徑 + 83 海路），有座標點序列
- **71 地標**（客棧、礦脈、遺跡、地牢、戰場、神聖森林...），有座標
- **9 動態事件區**（入侵、飢荒、乾旱、洪水...），有影響範圍
- **4659 條筆記**（軍團建制、戰爭歷史、事件紀錄）
- **383 條河流**，有名字、長度、寬度、流域

### 降採樣策略

7691 格太細。兩種聚合粒度可選：

**方案 A：省級聚合（粗）**
1. 同 province 的 cell 合併為一個房間
2. 房間名 = province.fullName
3. zone = state.name
4. tag = 該 province 內最多的 biome
5. exits = 跨 province 的 cell neighbor 關係（去重後）
6. 607 省 → 扣海洋 → 預估 **~300 個世界房間**

**方案 B：城鎮級直出（細）**
1. 每座 burg = 一個房間（623 格）
2. 路線（roads/trails）= Exit 連線
3. 非城鎮的省份 = 野外過渡房間
4. 預估 **~800 個世界房間**

可混合：核心區域用方案 B（城鎮密集處），邊陲用方案 A（荒野大片合併）。

### Celia 城鎮 → Watabou 參數對接

Azgaar burgs 自帶的旗標可直接餵 Watabou：

| Azgaar burg 屬性 | Watabou 參數 |
|-------------------|-------------|
| `citadel: 1` | `citadel=1`（城內有城堡） |
| `plaza: 1` | `plaza=1`（有廣場） |
| `port: 1` | `coast=1`（臨海） |
| `population` | `size` 參數（人口→城市規模） |
| `capital: 1` | 規模加大、加 `walls=1` |

### 設計者校對點

- 降採樣粒度選擇（省級 / 城鎮級 / 混合）
- 哪些城鎮優先展開（接入 Watabou 層）
- 名稱翻譯/改名（英文 → 世界觀命名）
- 地標類型對應（mines→資源點、dungeons→危險區、inns→聚念場休息點）
- 動態事件區對應（Invasion→戰亂、Famine→飢荒 → 影響聚念場強度？）

## §三：Watabou → 地點內部（Parser B / C）

Watabou 只在玩家需要進入某城鎮/地點時才使用。**按需生成，不是一次做完。**

### 原始資料（已驗證：greytide.json，City 類型）

- 道路為 LineString，無共用座標，需幾何推算拓撲
- District 帶名字的 Polygon
- 建築為 MultiPolygon（裝飾用，掛到最近路口）

### 拓撲推算演算法

1. **收集所有道路座標點**（端點 + 中繼點）
2. **近鄰聚類**（eps ≈ 15）：距離內的點合併為一個節點
3. 多條道路的點落入同一聚類 = **路口 = 房間節點**
4. 同一條道路上相鄰兩個聚類 = **路段 = Exit 連線**
5. **Point-in-polygon**：節點落入哪個 district → zone
6. **最近路口歸屬**：建築掛到最近路口 → 該房間的 objects

### 各生成器對應 Celia 地標

| Watabou 生成器 | 觸發條件（Celia 資料） | 預估房間數 |
|---------------|----------------------|-----------|
| City | burg.population 高、capital=1 | 60~120 |
| Village | burg.population 低 | 15~30 |
| Cave/Glade | marker.type = mines, caves, sacred-forests | 5~20 |
| Dungeon | marker.type = dungeons, ruins, necropolises | 10~40 |
| Dwelling | 城內特定建築（商店、旅店） | 3~10 |

## §四：工作流程（大到小）

```
第一步：Celia 已選定（seed: 938784876，設計者親手調過）
  ↓ Full JSON 已匯出（9MB）

第二步：Parser A 轉世界地圖
  ↓ 讀 Celia Full JSON → 省級/城鎮級聚合 → rooms.json
  ↓ 路線（roads/trails/searoutes）→ Exit 連線
  ↓ 地標（markers）→ 特殊房間 tag
  ↓ 設計者用 map_viewer 校對（改名、世界觀適配）

第三步：選定首批展開城鎮（設計者決定）
  ↓ 從 623 座中選 3~5 座優先展開
  ↓ burg 旗標（citadel/plaza/port）自動對應 Watabou 參數

第四步：Watabou 生成城鎮內部
  ↓ 設計者在 Watabou 網頁調 seed 直到滿意
  ↓ 匯出 JSON → Parser B → 追加進 rooms.json
  ↓ 城鎮入口 ↔ 世界地圖房間 雙向連線

第五步：描述生成
  ↓ 碼農腳本按 tag + zone 批量生成（Plan B：描述 = 純氛圍文字）
  ↓ 設計者抽查

第六步：上線測試 → 按需繼續展開更多城鎮/地點
```

## §五：工作流程（小到大）

場景：設計者腦中冒出一座新村莊。

```
第一步：Watabou Village 生成 → Parser B → 村莊房間

第四步：描述生成 → 校對 → 完成
```

不需要從 Azgaar 重新跑。世界地圖是骨架，隨時可以往上掛新的肉。

## §九：風險與備註

1. **Cells GeoJSON 和 Full JSON 是兩種匯出格式**。Cells 只有數字索引；Full JSON 帶完整名稱和對照關係。Parser A 應以 Full JSON 為輸入源
2. **Watabou 的幾何推算有 epsilon 敏感性**。eps 太小漏路口，太大合併錯誤。生成後必須在 map_viewer 裡視覺確認
3. **手刻的 639 格不必立即廢棄**。先用新管線生成一座測試城市，確認品質後再決定是否替換
4. **623 座城鎮按需展開**。不是一次做完。先做 3~5 座，驗證管線，再逐步擴張
5. **這不是一天的事。但每一步都是機械性工作。** 設計者只需要：調參數、看圖、改名字、說「好」或「不好」
