> **存檔註（2026-04）**：§一～§五 多為遷移前診斷；**現行建置與目錄結構以 `cargo` 與 `src/` 為準**，舊版指令／檔名僅作存檔參照。

> 建立日期：2026-03-22
> 版本：v1.1（整合稽核數字與回饋意見）
> 狀態：**已完成**（2026-02-12：§六各項已落地；細部理想值如 `main` 行數可另開迭代）

## 一、現況診斷

### 1.1 `db/` 是神包（God Package）

**規模**：37 個檔案、約 6502 行，是全專案最大的包。

`db/` 名義上是資料存取層，但實際混入三類責任：

| 分類 | 檔案 | 實際職責 |
|------|------|------|
| 資料存取（正確） | `entity`, `room`, `npc`, `inventory`, `equip` | 讀寫 store |
| **業務邏輯（已遷 `npc/`）** | ~~`decision` 等~~ → 見 `npc/` | NPC 決策、話題、微互動、反應、行為 JSON、撮合、未觀測 tick |
| **演算法** | `pathfind` | 路徑尋找（撮合已遷 `npc/job_matching`） |
| **交易流程（錯置）** | `trade_pending`, `trade_resolve`, `npc_trade` | 議價、結算 |
| ~~殘留~~ | ~~`sqlite`~~ | ~~已刪除~~（2026-02-12：P1 落地，僅 `store`） |

後果：所有包都 import `db`，`db` 成為全域耦合點，任何改動都可能波及全局。

---

### 1.2 `*sql.DB` 殘留（**已清除**，2026-02-12）

~~SQLite 已於 v0.10 完成 JSON/store 遷移……~~ **現況**：`database/sql` 與 `modernc.org/sqlite` 已自產物碼與舊模組清單移除；`db`／`server`／`game`／`event`／`economy`／`npcnpc`／`main` 之 API 改為僅依賴 `store.Default`（未初始化時回傳 `db.ErrNoStore` 等）。測試以 `store.Init`＋暫存目錄為準（見 `db/schedule_test` 之 `setupTestStore`）。

### 1.7 `data/` 與 `config/` 結構不一致

```
data/rooms.json                 ← （歷史）根層合併檔；**2026-02-12 起已自版控移除**
data/rooms/**.json              ← **執行期**：遞迴掃描一房一檔（主體 `editor/`）；見 `data/rooms/README.md`
data/rooms/editor/              ← 編輯主力目錄
data/config/                    ← gametext.json、server_defaults.json、simulation.json
data/templates/llm_prompts.json ← LLM 提示詞（在 templates，非 config）
config/config                ← 設定載入（現行見 `src/config/`）
config/server_defaults       ← 與 data/config/ 有對應關係但路徑分散
```

> **現況補註**：伺服器載房不依賴根層 `data/rooms.json`；若需單檔瀏覽可執行 `node tools/js/merge-rooms-one-per-line.js` 產生**可選**合併產物（不必入版控）。

JSON 配置與程式內預設互相映射，但分散在不同路徑，關係仍待長期收斂（本節保留為歷史診斷）。

## 二、整頓目標

1. **`db/` 只做資料存取**：業務邏輯移出，包大小降至 ~3000 行以內
2. **清除 `*sql.DB` 殘留**：移除死參數、死依賴、`modernc.org/sqlite`
3. **進入點維持薄層**：`src/main.rs` 僅啟動；業務在 `src/lib.rs` 與各子模組
4. **對話規則評分**：集中在 `src/ai/scorer.rs`
5. **`src/server` 按領域切分**：避免單檔過大
6. **工具程式統一整理**：維護腳本與 CLI 各有去處
7. **`docs/` 重新分區**：可搜尋、可導航

### 階段二：清除死碼（改動廣，每個改動都是減法）

**P1 — 移除 `*sql.DB` 殘留**

1. 將 `db/` 各函數的 `db *sql.DB` 參數移除，改為直接存取 `store.Default`
2. 刪除 `db/sqlite`（`OpenDB` 可移入測試 helper，集中於 `db/testutil_test`）
3. 從各呼叫方（`src/main.rs` 啟動鏈、`server/`、`game/`、`economy`、`event`）移除 `database/sql` import
4. 依賴整理並移除 `modernc.org/sqlite` 及其間接依賴（歷史步驟；現行見 `Cargo.lock`）
5. 測試（`db/schedule_test`、`db/npc_activation_simulation_test`）改用 `store.Init` 搭配 temp 目錄

驗收（歷史，已落地）：
- 產物碼可建置、測試通過（現行：`cargo build`、`cargo test`）
- 正式路徑不再依賴 `database/sql` 直連 SQLite 產物檔

**架構契約（執行後寫入 CLAUDE.md 或 README）**：正式執行路徑只認 `store`，不支援直接 SQLite；測試用 DB helper 集中於 `db/testutil_test`，不得散落。

### 階段三：結構重組（工程量最大，需充分測試）

**P4 — 切分 `db/` 業務邏輯**

從 `db/` 分離出業務邏輯，建立 `npc/` 子系統包：

```
npc/
  decision           ← 原 db/decision（決策引擎、SurvivalLineMg）
  topics             ← 原 db/npc_topics（話題選擇）
  social             ← 原 db/npc_social（微互動敘事）
  reaction           ← 原 db/npc_reaction（行為反應）
  movement           ← 原 db/npc_movement（TravelerManager、MovementDef）
  job_matching       ← 原 db/job_matching（職業撮合）
  behavior           ← 原 db/behavior（npc_behaviors.json、閒置／換班／巡邏文案）
  unobserved         ← 原 db/unobserved（無人觀測背景 tick）
  activation_simulation_test ← 原 db 內移動相關兩則測試（避免 db 測試 import npc 循環）
  topics_test        ← 原 db/npc_topics_test
```

> **依賴邊界**：`npc` **可** `import "singularity_world/db"` 做資料讀寫；**`db` 不得 import `npc`**（避免循環）。`npc/` 不得反向依賴 `game/`。原則：排程 tick 留 `game/`，規則引擎放 `npc/`。

整頓後 `db/` 應只剩：

| 檔案 | 職責 |
|------|------|
| `entity`, `room`, `room_object` | 實體與房間讀寫 |
| `npc`, `npc_memory` | NPC 基本讀寫 |
| `inventory`, `equip` | 背包裝備讀寫 |
| `archival`, `backstory` | 記憶與背景讀寫 |
| `schedule`, `assignment`, `occupation` | 排班指派讀寫 |
| `auth` | 玩家認證 |
| `pathfind` | 可考慮後續移入 `world/`（地圖包已存在） |

驗收：`cargo build`、`cargo test` 全過。

---

**P5 — 切分 `server/handler`**（**已完成** 2026-02-12）

實際檔名（同包、不改 WS 協定）：

```
server/
  handler                      ← `HandleMessage` dispatch
  handler_context              ← `currentGameHour`、`defaultObserver`、`sendError`、`mustJSON`、`BroadcastRoomViews` 等
  handler_auth                 ← login、create_character、loginSuccess
  handler_move                 ← move、房間 view、me、離房觀測
  handler_action               ← `handleDoAction` 入口與參數檢查
  handler_action_entity_dispatch ← 角色分支薄 dispatch（轉呼叫 action_entity_*）
  handler_action_object_dispatch ← 物件分支薄 dispatch（轉呼叫 action_object_*）
  action_entity_validate       ← `entitySocketOK`（插座／職場）
  action_entity_look           ← Look
  action_entity_talk           ← Talk
  action_entity_combat         ← Subdue／Slay
  action_entity_borrow         ← Borrow
  action_entity_trade          ← Trade
  action_object_resolve        ← 解析同房物件與插座
  action_object_narrative      ← `buildObjectActionNarrative`
  action_object_move           ← Move 切房
  action_object_followup_buttons ← 其餘動詞／Look→門 fallback
  action_narrative_look        ← `buildLookNarrative`
  action_narrative_talk        ← `buildTalkNarrative`
  action_narrative_combat      ← `buildAttackNarrative`
  action_trade_input           ← `isTradeRejectInput`
  handler_inventory            ← entity_status、inventory、equip／unequip、pushRefresh
  handler_debug                ← topology_debug
  room_editor_dispatch         ← `HandleRoomEditorAPI` 路由
  room_editor_types            ← 編輯器 JSON 型別
  room_editor_persist          ← layout／房間檔讀寫、`ensureStoreRoom`
  room_editor_handler_graph    ← GET graph
  room_editor_handler_crud     ← 房間 POST／PUT／DELETE
  room_editor_exit_helpers     ← 出口與 Move 物件同步
  room_editor_handler_link     ← 連結 POST／DELETE
  room_editor_handler_layout   ← PUT layout
```

根目錄 **`main` 套件**（啟動與模擬迴圈分檔，同包不分目錄）：

```
main                  ← `main`：目錄／store／hub／`registerHTTPRoutes`、`startSimulationMainLoop`、Listen
http_routes           ← HTTP／WS 路由註冊
brain_arrival         ← `buildActiveRoomIDs`、`applyBrainArrivalEffects`
simulation_main_loop  ← Observer、TravelerManager、`game.Loop` 本體
```

> **原則**：do_action 相關為「主幹 dispatch + 單一職責樹葉檔」；新增動詞時優先新增 `action_entity_*` 或 `action_object_*` 一片樹葉，再於對應 dispatch `switch` 接上。

驗收：`cargo build`、`cargo test（server 模組）` 通過；WS smoke 建議手動跑 §四清單。

## 四、各階段驗收與提交原則

每個階段完成後執行：

```bash
cargo build
cargo test
```

**提交類型區分**（利於回滾與 code review）：
- `refactor(move):`：僅搬移檔案，不改行為
- `refactor(sig):`：改函數簽名或依賴關係
- `refactor(rm):`：刪除死碼

**P4/P5 完成後須補手動 smoke 清單**，涵蓋 `cargo test` 未覆蓋的 WebSocket 路徑：
- WS 登入 / 登出
- 移動命令
- NPC 對話觸發
- 交易流程
- 管理命令

## 五、暫不執行的事項

| 事項 | 原因 |
|------|------|
| `data/rooms.json` 根層去留 | 存在兩類用途：工具鏈（例如 `node tools/js/merge-rooms-one-per-line.js` 產生合併檔）和執行期 API（`GET /data/rooms.json` 由 `src/server` 從 store 動態彙總，不依賴實體根層檔）。去留前須分別評估 |
| `src/config` 與 `data/config/` 整合 | 涉及設定載入邏輯，另案討論。初步原則：人類可編輯的預設值以 `data/config/*.json` 為準；Rust `config` 模組負責載入與型別 |
| `economy/` 與交易邏輯合併 | 待 P4 完成後評估 |
| `combat/` 與主迴圈整合 | 功能尚未完整，暫不動 |
| `model/` 改名為 `types/` | 現有設計理由正確，時機不成熟 |
