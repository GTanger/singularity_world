> 建立日期：2026-03-22

## 一、現況診斷

### 1.1 `db/` 是神包（God Package）

**規模**：37 個檔案、約 6502 行，是全專案最大的包。

`db/` 名義上是資料存取層，但實際混入三類責任：

| 分類 | 檔案 | 實際職責 |
|------|------|------|
| 資料存取（正確） | `entity.go`, `room.go`, `npc.go`, `inventory.go`, `equip.go` | 讀寫 store |
| **業務邏輯（已遷 `npc/`）** | ~~`decision.go` 等~~ → 見 `npc/` | NPC 決策、話題、微互動、反應、行為 JSON、撮合、未觀測 tick |
| **演算法** | `pathfind.go` | 路徑尋找（撮合已遷 `npc/job_matching.go`） |
| **交易流程（錯置）** | `trade_pending.go`, `trade_resolve.go`, `npc_trade.go` | 議價、結算 |
| ~~殘留~~ | ~~`sqlite.go`~~ | ~~已刪除~~（2026-02-12：P1 落地，僅 `store`） |

後果：所有包都 import `db`，`db` 成為全域耦合點，任何改動都可能波及全局。

~~SQLite 已於 v0.10 完成 JSON/store 遷移……~~ **現況**：`database/sql` 與 `modernc.org/sqlite` 已自產物碼與 `go.mod` 移除；`db`／`server`／`game`／`event`／`economy`／`npcnpc`／`main` 之 API 改為僅依賴 `store.Default`（未初始化時回傳 `db.ErrNoStore` 等）。測試以 `store.Init`＋暫存目錄為準（見 `db/schedule_test.go` 之 `setupTestStore`）。

### 1.7 `data/` 與 `config/` 結構不一致


JSON 配置與 Go 配置互相映射，但分散在不同路徑，關係不明確。

## 二、整頓目標

1. **`db/` 只做資料存取**：業務邏輯移出，包大小降至 ~3000 行以內
2. **清除 `*sql.DB` 殘留**：移除死參數、死依賴、`modernc.org/sqlite`
3. **`main.go` 回到入口職責**：業務函數移入對應包，行數降至 ~200 行
4. **`dialogue_scorer.go` 歸位**：移入 `ai/`
5. **`server/handler.go` 按領域切分**：單檔縮至 ~300 行以內
6. **工具程式統一整理**：Go 工具和腳本各有去處
7. **`docs/` 重新分區**：可搜尋、可導航

### 階段三：結構重組（工程量最大，需充分測試）

**P4 — 切分 `db/` 業務邏輯**

從 `db/` 分離出業務邏輯，建立 `npc/` 子系統包：

```
npc/
  decision.go           ← 原 db/decision.go（決策引擎、SurvivalLineMg）
  topics.go             ← 原 db/npc_topics.go（話題選擇）
  social.go             ← 原 db/npc_social.go（微互動敘事）
  reaction.go           ← 原 db/npc_reaction.go（行為反應）
  movement.go           ← 原 db/npc_movement.go（TravelerManager、MovementDef）
  job_matching.go       ← 原 db/job_matching.go（職業撮合）
  behavior.go           ← 原 db/behavior.go（npc_behaviors.json、閒置／換班／巡邏文案）
  unobserved.go         ← 原 db/unobserved.go（無人觀測背景 tick）
  activation_simulation_test.go ← 原 db 內移動相關兩則測試（避免 db 測試 import npc 循環）
  topics_test.go        ← 原 db/npc_topics_test.go
```

> **依賴邊界**：`npc` **可** `import "singularity_world/db"` 做資料讀寫；**`db` 不得 import `npc`**（避免循環）。`npc/` 不得反向依賴 `game/`。原則：排程 tick 留 `game/`，規則引擎放 `npc/`。

整頓後 `db/` 應只剩：

| 檔案 | 職責 |
|------|------|
| `entity.go`, `room.go`, `room_object.go` | 實體與房間讀寫 |
| `npc.go`, `npc_memory.go` | NPC 基本讀寫 |
| `inventory.go`, `equip.go` | 背包裝備讀寫 |
| `archival.go`, `backstory.go` | 記憶與背景讀寫 |
| `schedule.go`, `assignment.go`, `occupation.go` | 排班指派讀寫 |
| `auth.go` | 玩家認證 |
| `pathfind.go` | 可考慮後續移入 `world/`（地圖包已存在） |

驗收：`go build ./...`、`go test ./...` 全過。

---

**P5 — 切分 `server/handler.go`**（**已完成** 2026-02-12）

實際檔名（同包、不改 WS 協定）：

```
server/
  handler.go                      ← `HandleMessage` dispatch
  handler_context.go              ← `currentGameHour`、`defaultObserver`、`sendError`、`mustJSON`、`BroadcastRoomViews` 等
  handler_auth.go                 ← login、create_character、loginSuccess
  handler_move.go                 ← move、房間 view、me、離房觀測
  handler_action.go               ← `handleDoAction` 入口與參數檢查
  handler_action_entity_dispatch.go ← 角色分支薄 dispatch（轉呼叫 action_entity_*）
  handler_action_object_dispatch.go ← 物件分支薄 dispatch（轉呼叫 action_object_*）
  action_entity_validate.go       ← `entitySocketOK`（插座／職場）
  action_entity_look.go           ← Look
  action_entity_talk.go           ← Talk
  action_entity_combat.go         ← Subdue／Slay
  action_entity_borrow.go         ← Borrow
  action_entity_trade.go          ← Trade
  action_object_resolve.go        ← 解析同房物件與插座
  action_object_narrative.go      ← `buildObjectActionNarrative`
  action_object_move.go           ← Move 切房
  action_object_followup_buttons.go ← 其餘動詞／Look→門 fallback
  action_narrative_look.go        ← `buildLookNarrative`
  action_narrative_talk.go        ← `buildTalkNarrative`
  action_narrative_combat.go      ← `buildAttackNarrative`
  action_trade_input.go           ← `isTradeRejectInput`
  handler_inventory.go            ← entity_status、inventory、equip／unequip、pushRefresh
  handler_debug.go                ← topology_debug
```

> **原則**：do_action 相關為「主幹 dispatch + 單一職責樹葉檔」；新增動詞時優先新增 `action_entity_*` 或 `action_object_*` 一片樹葉，再於對應 dispatch `switch` 接上。

驗收：`go build ./...`、`go test ./server/...` 通過；WS smoke 建議手動跑 §四清單。

## 四、各階段驗收與提交原則

每個階段完成後執行：

```bash

```

**提交類型區分**（利於回滾與 code review）：
- `refactor(move):`：僅搬移檔案，不改行為
- `refactor(sig):`：改函數簽名或依賴關係
- `refactor(rm):`：刪除死碼

**P4/P5 完成後須補手動 smoke 清單**，涵蓋 `go test` 未覆蓋的 WebSocket 路徑：
- WS 登入 / 登出
- 移動命令
- NPC 對話觸發
- 交易流程
- 管理命令

## 五、暫不執行的事項

| 事項 | 原因 |
|------|------|
| `data/rooms.json` 根層去留 | 存在兩類用途：工具鏈（`SyncRoomsFromFile`、`tools/go/split_rooms` 直接讀寫此檔）和執行期 API（`GET /data/rooms.json` 由 `server/api_rooms_data.go` 從 store 動態彙總，不依賴實際檔案）。去留前須分別評估兩類用途的可替代性 |
| `config/` 與 `data/config/` 整合 | 涉及設定載入邏輯，另案討論。初步原則：人類可編輯的預設值以 `data/config/*.json` 為準；`config` package 只負責載入與型別定義 |
| `economy/` 與交易邏輯合併 | 待 P4 完成後評估 |
| `combat/` 與主迴圈整合 | 功能尚未完整，暫不動 |
| `model/` 改名為 `types/` | 現有設計理由正確，時機不成熟 |
