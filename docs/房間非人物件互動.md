# 房間非人物件互動系統

> 最後更新：2026-03-12；§2.3 導航與出口融合、點擊分流、取消出口欄（依 ui變更chat 討論）  
> 狀態：已實作（11.1～11.7）；物件來源為**各房間 JSON 的 objects 欄位**；歸屬權／偷竊／有狀態物件為後續階段  
> 依賴：插頭插座語義（決策 002）、NPC 活化系統、房間制

---

## 一、概述

目前房間制下，玩家的互動對象僅限於「人」（NPC / 玩家），房間描述雖然提到了宮燈、匾額、蒸籠、陶甕、捲軸等物件，但這些全是純文字裝飾，不可觸碰、不可操作。

**本系統的目標**：讓房間中的非人物件成為可互動的一等公民，與角色共享同一套插頭插座語義，並引入歸屬權機制，使互動產生真實的社會後果。

**核心原則**：

- **描述即物件**：房間描述裡出現的可互動物件，在描述文字中以富文字標記（色彩 + 可點擊），玩家一眼即知「這東西可以摸」。
- **環境基調**：房間格環境描述（description）生成時，以 [世界觀：富態與拉鋸](reference/世界觀：富態與拉鋸.md) 為參考，使敘事符合富態／拉鋸／無廢土／惡地亦有生機／危險仍危險等基調。
- **插頭插座統一**：非人物件與角色使用相同的 `do_action` 流程，後端判斷可執行性，前端不猜測。
- **歸屬權真實**：有主之物受保護，無主之物自由取用，偷竊需四下無人，被發現有後果。

## 二、前端 UI 設計

### 2.1 房間描述富文字標記

現有的 `formatDesc()` 已將 `【文字】` 渲染為綠色 `.desc-highlight`。非人物件將延伸此機制：

**規則**：房間描述中，可互動物件以 `〔物件名〕` 標記（注意使用全形方頭括號，與 NPC 名字的 `【】` 區分）。

**渲染效果**：

| 標記 | 用途 | 前端樣式 |
|------|------|---------|
| `【名字】` | 人物名（已有） | 綠色 `.desc-highlight` |
| `〔物件名〕` | 可互動物件 | 琥珀色 `.desc-object`，帶底線虛線，hover 變亮 |

**範例**：

```
原始描述（房間 JSON 的 description）：
"挑高的大廳中央懸著一盞〔六角宮燈〕，暖黃的光暈映在兩側的木柱上。
櫃台後方掛著一面寫有【浮生】二字的〔匾額〕，墨跡蒼勁。
角落立著一塊〔佈告欄〕，上頭釘滿了紙條。"

渲染結果：
「六角宮燈」「匾額」「佈告欄」以琥珀色顯示，玩家可直接點擊。
```

**點擊行為**：依物件類型分流（詳見 §2.3）。**建築／商鋪類**（門、店舖、民宅）：點擊 → 先送出「觀看」，Log 出現描述與【進入】等動作。**巷道／路段類**（街道延伸、緩坡、巷口）：可設為點擊即送出 `Move`，直接切換房間。其餘純觀賞物件仍為點擊 → 觀看，下一行顯示【閱讀】【嗅聞】等。

### 2.2 點擊即觀看 + Log 下一行其他動作（現行實作）

物件與人物採用同一套互動邏輯，不另設浮動下拉或手風琴。

**互動流程**：

```
1. 玩家點擊描述中的 〔匾額〕 或人物欄的「經理」
2. 前端立即送出 do_action { entity_id: ..., action: "Look" }
3. 伺服器回傳 action_result，觀看敘事 append 到 Log
4. main.js 依 target_id 從 state.objects 或 state.entities 取得其他動作（排除 Look），
   在敘事下一行 append 可點擊的【閱讀】【對話】【攻擊】等
5. 玩家點擊 Log 中的【閱讀】→ 送出 do_action Read → 結果再 append 到 Log
```

**人物欄**：同房 NPC/玩家以列表顯示（▸ 名稱），點擊即送觀看，不再有手風琴展開動作列；其他動作（對話、攻擊）同樣在 Log 觀看敘事的下一行顯示。

**樣式對照**：

| 元素 | 說明 | 色彩 |
|------|------|------|
| `〔物件名〕` 常態 | 琥珀色 + 虛底線、可點擊 | `#ffb74d` |
| `〔物件名〕` hover | 亮琥珀色 + 實底線 | `#ffa726` |
| Log 內其他動作 | `.log-object-action`，可點擊 | `#ffb74d`，hover `#ffa726` |

### 2.3 導航與出口融合（UI 變更）

為減少「選單感」、讓導航回歸描述中的物理物件，採用**出口融合進描述**與**點擊分流**，必要時可**取消傳統 UI 出口欄**。

#### 2.3.1 雙軌：資料保留、UI 可隱藏

- **資料層**：房間 JSON 的 `exits` 陣列**一律保留完整**，供 NPC 尋路（A 點到 B 點）使用，不得因 UI 調整而刪除。
- **可選**：在 `exits` 單筆中新增 `"ui_hidden": true`。前端渲染出口按鈕時**略過**標記為隱藏的出口；玩家僅能透過描述中的 `〔物件名〕` 觸發移動。
- **效果**：NPC 仍依 `exits` 尋路；玩家依描述與物件點擊移動，介面可極簡。

#### 2.3.2 點擊行為分流

| 物件類型 | 點擊後行為 | 說明 |
|----------|------------|------|
| **巷道／路段**（如〔大街三段〕、〔前方緩坡〕、〔狹窄巷口〕） | **直接 Move** | 點擊即送 `do_action { action: "Move" }`，不先 Look；符合「在長街上行走」的流暢位移感。 |
| **建築／商鋪／住宅**（如〔焦黑木門〕、〔藥舖〕、〔民宅一〕） | **先 Look，再選擇進入** | 點擊送 `Look`，Log 顯示該建築的物理白描（門的質地、鎖的狀態等），下一行出現【進入】或【推門】；點擊後才送 Move／Enter。增加「進入前」的觀察與儀式感。 |

**實作約定**：巷道類物件的 `sockets` 以 `Move` 為主（可僅含 `Move`，或 Move 為預設優先）；建築類以 `Look` 為首，並含 `Move` 或 `Enter`，供 Log 下一行選擇。

#### 2.3.3 取消傳統出口欄

在已實作 `Move` 且出口皆鑲嵌於描述與 `objects` 的前提下，**可完全取消傳統的 UI 出口按鈕列**。玩家僅透過描述中的 `〔〕` 與 Log 內的【進入】等動作移動；必要時可保留極簡的「當前位置」標籤（如：浮生城・1F）或 Debug 用出口列表。

#### 2.3.4 描述與出口的對應

- 房間 `description` 末尾應自然帶出「通往哪裡」：例如「延伸向〔大街三段〕的坡道」「左側一道〔焦黑木門〕」。
- 每個可移動目標須在該房 `objects` 中有對應物件，且 `sockets` 含 `Move`（或建築類含 Look + Move／Enter）；物件可透過 `move_to_room_id` 或與 `exits[].to` 對應，由後端執行切房。

## 三、物件定義格式

### 3.1 資料來源：各房間 JSON 的 `objects` 欄位

物件**寫在該房間的 JSON 檔內**，與房間的 `id`、`name`、`description`、`exits` 同檔。一房一檔目錄為 `data/rooms/`（依 zone／子區域分層），模板與欄位說明見 **`data/rooms/README.md`**。

範例（`data/rooms/editor/city_life_1f.json` 片段）：

```json
{
  "id": "life_hall",
  "name": "浮生大廳",
  "description": "挑高的大廳中央懸著一盞〔六角宮燈〕，櫃台後方掛著〔匾額〕，角落立著一塊〔佈告欄〕。",
  "zone": "citylife",
  "exits": [ ... ],
  "objects": [
    {
      "id": "life_hall_lantern",
      "name": "六角宮燈",
      "owner": "inn",
      "sockets": ["Look"],
      "responses": {
        "Look": "你抬頭端詳那盞六角宮燈。燈罩以薄絹繃製，繪有松鶴延年的紋樣，燭火搖曳間，六個面輪流明滅，在天花板上投下旋轉的光影。"
      }
    },
    {
      "id": "life_hall_plaque",
      "name": "匾額",
      "owner": "inn",
      "sockets": ["Look", "Read"],
      "responses": {
        "Look": "匾額掛在櫃台正上方，寬約三尺，厚實的檀木板面已被歲月磨出深沉的包漿。",
        "Read": "匾上以行草寫著【浮生】二字，筆勢蒼勁飛揚，落款處隱約可見一枚朱紅小印，年代已不可考。"
      }
    }
  ]
}
```

### 3.2 欄位定義（目前實作）

| 欄位 | 型別 | 必填 | 說明 |
|------|------|------|------|
| `id` | string | 是 | 全域唯一識別符，建議格式 `{room_id}_{物件代號}` |
| `name` | string | 是 | 顯示名稱，**須與房間 description 中 `〔〕` 內文字一致**，前端才能對應點擊 |
| `owner` | string | 選 | 歸屬權標記（詳見 §四），空字串 = 無主 |
| `sockets` | string[] | 是 | 可用動詞（插座），如 `["Look", "Read", "Smell"]` |
| `responses` | map | 是 | 動詞 → 敘事文字，key 須在 `sockets` 內 |

**導航用欄位（與 §2.3 出口融合對接）**：若物件可觸發移動，可於物件上擴充 `move_to_room_id`（或與房間 `exits` 中某筆的 `to` 對應），後端執行 `Move` 時依此切換玩家房間。

**後續階段（規劃中，尚未實作）**：`owner_guard`、`use_blocked`、`use_steal`、`ambient`、`state`、`state_responses` 等，見 §四、§九。

### 3.3 動詞（插座）列表

沿用決策 002 的動詞體系，針對非人物件常用的：

| 動詞 | 說明 | 典型目標 |
|------|------|---------|
| `Look` | 仔細端詳外觀 | 所有物件 |
| `Move` | 移動過去／走過去／進入 | 門、樓梯、通道、出口（點擊後角色移動至該處或進入連通房間） |
| `Read` | 閱讀文字內容 | 匾額、佈告欄、書籍、捲軸 |
| `Use` | 操作/使用 | 灶台、井、磨刀石、織布機 |
| `Open` | 開啟 | 箱子、門、抽屜 |
| `Unlock` | 解鎖 | 上鎖的門、上鎖的箱子／櫃子（需持有對應鑰匙或解鎖工具） |
| `BreakLock` | 破壞鎖 | 上鎖的門、上鎖的物件（需工具或足夠力道，可能觸發聲響／損壞） |
| `Sit` | 坐下 | 椅子、長凳、蒲團 |
| `Smell` | 嗅聞 | 香爐、酒甕、花草 |
| `Taste` | 品嚐 | 酒甕、食物 |
| `Take` | 拾取/摘取 | 野花、草藥、掉落物 |
| `Chop` | 砍伐 | 樹木、柴堆 |
| `Operate` | 操作機關 | 機關、暗門、絞盤 |

## 四、歸屬權模型

### 4.1 歸屬權分類

```
歸屬權
├── 無主（owner: ""）
│   ├── 公共設施：佈告欄、路標、官井 → 任何人自由互動
│   └── 野生資源：花草、樹木、礦石 → 自由採集/砍伐
│
├── 有主（owner: "inn" / "npc_id" / "faction_id"）
│   ├── 可觀看：Look / Read 不受限，所有人可觀看有主之物
│   ├── 需授權才可使用：Use / Open / Take 等操作性動詞需檢查權限
│   │   ├── 看守者在場 → 被制止（use_blocked 敘事）
│   │   ├── 看守者不在場、其他人在場 → 行為被目擊（有後果）
│   │   └── 四下無人 → 可偷用（use_steal 敘事，觸發偷竊事件）
│   └── 可租借：owner_rentable = true → 付費後獲臨時使用權
│
└── 玩家所有（owner: "player:{player_id}"）
    └── 未來擴充：玩家擁有的房產內之物件，他人互動同上規則
```

### 4.2 權限判定流程

```
玩家對有主物件執行操作性動詞（Use / Open / Take / Chop …）
│
├─ 動詞是 Look / Read / Smell？
│  └─ 直接通過，回傳 responses 敘事（觀看不受限）
│
├─ owner 為空？
│  └─ 直接通過，回傳 responses 敘事（無主之物）
│
├─ 玩家擁有授權（租借/擁有者本人）？
│  └─ 直接通過
│
├─ 檢查同房是否有 owner_guard 中的 NPC
│  ├─ 有看守者在場 → 阻止，回傳 use_blocked 敘事
│  │   （看守者 NPC 產生對應的 narrate 反應）
│  │
│  ├─ 無看守者，但有其他 NPC 或玩家在場
│  │  └─ 行為被目擊 → 回傳偷竊敘事 + 記錄事件
│  │     （目擊者 NPC 可能產生反應：報警、喊叫、冷眼旁觀）
│  │
│  └─ 四下無人（房間內僅自己）
│     └─ 偷用成功 → 回傳 use_steal 敘事 + 記錄偷竊事件
│        （事件進入日誌，可能影響後續 NPC 對你的態度）
```

### 4.3 「四下無人」判定

「四下無人」= 同房間內除操作者外，沒有任何其他實體（NPC 或玩家）。

```rust
// 概念：同房僅玩家一人。實作見 `crate::db::get_entities_in_room`。
fn is_alone(room_id: &str, player_id: &str, game_hour: i32) -> bool {
    let entities = db::get_entities_in_room(room_id, game_hour).unwrap_or_default();
    entities.iter().all(|e| e.id == player_id)
}
```

### 4.4 偷竊後果（設計方向）

| 情境 | 後果 |
|------|------|
| 四下無人，偷用成功 | 事件記入日誌；物主方定期巡查，累積偷竊事件可能觸發追緝 |
| 有其他人目擊 | 事件記入日誌 + 目擊者記憶；NPC 可能當場反應（喊叫/報警） |
| 看守者在場被阻止 | 無實質後果，僅敘事；但頻繁嘗試可能降低好感度 |

## 五、後端架構

### 5.1 資料載入

- **來源**：各房間 JSON 檔（`data/rooms/` 下，一房一檔）內含選用欄位 `objects`。
- **流程**：`store` 載入各房 JSON 時一併讀取 `objects`；`db::get_objects_in_room` 等直接依當前房間資料查詢（見 `src/db/room_object.rs`、`store` 載入路徑）。
- **查詢**：`db.GetObjectsInRoom(roomID)`、`db.GetObjectByIDInRoom(roomID, objectID)`（同房優先，避免跨房重複 id）、`db.GetObjectByNameInRoom(roomID, name)`、`db.GetObjectAndRoom(objectID)`（全域 id，作為後備）等皆從此快取讀取。`do_action` 解析物件時順序為：同房 ID → 同房名稱 → 全域 ID。
- **靜態檢查**：`src/roomcheck` + `cargo run --bin checkrooms`；正式啟動前與 **`./start`** 閘門一致：`cargo clippy`、`cargo test`、**`checkrooms -brackets -strict`**（Move／Look 契約 + 〔〕必對應 `objects[].name`），失敗則中止建置。手動：`cargo run --bin checkrooms -- -brackets -strict`。見根目錄 `README.md`、`data/rooms/README.md`。

房間內物件型別見 **`src/model/mod.rs`** 之 `RoomObject`（serde 欄位與 JSON 鍵一致）。

### 5.2 協議擴充

`RoomViewMsg` 含 `objects` 欄位（見 **`src/server/protocol.rs`**）：

```rust
#[derive(Serialize, Deserialize)]
pub struct ViewObject {
    pub id: String,
    pub name: String,
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub actions: Vec<String>,
}

// RoomViewMsg 內：`pub objects: Vec<ViewObject>`
```

### 5.3 `handleDoAction` 擴展

```
收到 do_action { entity_id: "life_hall_board", action: "Read" }
│
├─ 先查角色（現有流程）→ 找不到
├─ 再查物件（新增）→ 找到 life_hall_board
├─ 檢查物件是否在玩家同房間
├─ 檢查 HasSocket
├─ 檢查歸屬權（§4.2 流程）
└─ 回傳 action_result 敘事
```

### 5.4 物件環境敘事

物件的 `ambient` 欄位可被主迴圈的 idle tick 使用，與 NPC 閒置動作混合：

```
遊戲 tick → 有玩家的房間 → 隨機選物件或 NPC → 產生 ambient narrate
```

## 六、房間描述整合

### 6.1 描述文字規範

各房間 JSON 的 `description` 欄位中，可互動物件以 `〔物件名〕` 括起；**`〔〕` 內文字須與該房 `objects[].name` 一致**，前端才能對應點擊：

```json
{
  "id": "life_hall",
  "name": "浮生大廳",
  "description": "挑高的大廳中央懸著一盞〔六角宮燈〕，暖黃的光暈映在兩側的木柱上。櫃台後方掛著一面寫有【浮生】二字的〔匾額〕，墨跡蒼勁。角落立著一塊〔佈告欄〕，上頭釘滿了紙條。來往的旅人在此歇腳、打聽消息，或只是發呆望著門外。"
}
```

### 6.2 前端解析

`formatDesc()` 擴展，新增 `〔〕` 的解析規則。需將後端傳來的 `Objects` 陣列建成 name → id 的查找表，以便在描述解析時注入 `data-object-id`：

```javascript
// 快取當前房間物件（每次 view 更新時重建）
var currentRoomObjects = {}; // name → { id, actions }

function formatDesc(desc, objects) {
    if (!desc) return '';
    // 重建物件查找表
    currentRoomObjects = {};
    if (objects) {
        objects.forEach(function(o) { currentRoomObjects[o.name] = o; });
    }
    var safe = escapeHtml(desc);
    // 人物名：綠色
    safe = safe.replace(/【([^】]*)】/g,
        '<span class="desc-highlight">【$1】</span>');
    // 可互動物件：琥珀色，可點擊（僅當物件存在於 Objects 清單時才標記）
    safe = safe.replace(/〔([^〕]*)〕/g, function(match, name) {
        var obj = currentRoomObjects[name];
        if (obj) {
            return '<span class="desc-object" data-object-id="' + escapeHtml(obj.id)
                + '" data-object-name="' + escapeHtml(name)
                + '" role="button" tabindex="0">〔' + escapeHtml(name) + '〕</span>';
        }
        return '〔' + escapeHtml(name) + '〕'; // 無對應物件則純文字
    });
    return safe;
}
```

**實作（`web/mud-text.js`）補充**：`〔〕`／`【】` 先轉成帶 class 的 `<span>` 後，會在**這些 span 之外的純文字片段**內，再依 `objects[].name` 做後備替換（長名優先），讓「同段已有〔子區〕但仍須點大廳名」時不會整段跳過後備而困房。**仍須**讓每個可 `Move` 的 `name` 在 `description` 中至少出現一次（純文字或 `〔〕` 皆可）；若完全沒出現，前端無從產生可點區域。

### 6.3 點擊即送觀看與 Log 其他動作列

描述區委派事件監聽，點擊 `.desc-object` 時調用 `sendObjectLook(objectEl)`，直接送出 `do_action`、`action: "Look"`。人物欄點擊 NPC 列同樣送出 Look。`action_result` 抵達後，main.js 在 append 觀看敘事後，依 `target_id` 從 `state.objects` 或 `state.entities` 取得其他動作，append 一行 `.log-object-actions`（【閱讀】【對話】【攻擊】等），並在 `#log` 上委派 `.log-object-action` 點擊以送出對應 `do_action`。

## 八、與現有系統的對接

### 8.1 插頭插座（決策 002）

非人物件等同決策 002 §2.2「建築／結構」和 §2.4「其他可互動物件」的房間制實現。每個物件的 `sockets` 就是它的插座清單，`do_action` 就是插頭。

### 8.2 NPC 活化系統

- **物件 ambient**：物件的環境敘事池可與 NPC 閒置動作混合，由同一個 idle tick 驅動。
- **NPC 看守**：NPC 的歸屬（員工身份）與物件的 `owner_guard` 對應，NPC 在場時負責「守護」物件。
- **NPC 反應**：偷竊被目擊時，在場 NPC 根據其 personality（`behaviors/*.json` 的 `theft_reaction`）產生反應。

### 8.3 事件日誌

所有物件互動（特別是偷竊、使用有主物件）記入 `event/journal`，供觀測坍縮和 NPC 記憶系統使用。

### 8.4 經濟系統

- `Use` 灶台 → 消耗食材（背包物品）→ 產出食物（新物品）
- `Taste` 酒甕 → 消耗鎂 → 品酒體驗
- `Take` 野生資源 → 物品進入背包
- `Open` 寶箱 → 鎂/物品掉落

## 九、有狀態物件（進階）

部分物件有內部狀態，影響可用動詞和互動結果：

### 9.1 範例：門

```json
{
  "id": "life_storage_door",
  "name": "庫房門",
  "owner": "inn",
  "sockets": ["Look", "Open", "Operate"],
  "state": "locked",
  "responses": {
    "Look": "一扇厚實的木門，門閂上掛著一把銅鎖。"
  },
  "state_responses": {
    "locked": {
      "Open": "門被鎖住了，紋絲不動。",
      "Operate": "你需要鑰匙才能開鎖。"
    },
    "closed": {
      "Open": "你推開了門。",
      "Operate": "你將門閂推上。"
    },
    "open": {
      "Look": "門大開著，門後是堆滿雜物的庫房。"
    }
  }
}
```

### 9.2 狀態轉移

```
locked --[鑰匙或解鎖工具+Operate/Unlock]--> closed --[Open]--> open --[Operate]--> closed
       --[BreakLock]---------------------^         ^                    |
                                                                  |----[Open]----------+
```

狀態轉移邏輯由後端管理，前端只看到當下可用的動詞（不同狀態開放不同插座）。

### 9.3 上鎖的門與上鎖的物件：解鎖與破壞鎖

**上鎖**的門或物件（如櫃子、寶箱）具 `state: "locked"` 時，除一般 `Look` 外，可開放下列動作：

| 動詞 | 條件 | 結果 |
|------|------|------|
| **Unlock**（解鎖） | 玩家背包內持有**對應鑰匙**（與物件的 `key_item_id` 匹配）或**解鎖工具**（如撬鎖器、萬用鑰匙等，物品具 `unlock_tool: true` 或約定之類型） | 鎖開啟，狀態改為 `closed`（或依設計改為 `open`）；鑰匙／工具可保留或消耗依設計。 |
| **BreakLock**（破壞鎖） | 無需鑰匙；可選設計：需裝備工具（撬棍、斧頭）或屬性/技能門檻 | 鎖被破壞，狀態改為 `closed`／`open`；可能產生**聲響**（同房或鄰房 NPC 察覺）、**損壞敘事**（門框裂痕、鎖頭報廢），有主之物可能觸發歸屬權與偷竊後果。 |

**資料欄位建議**（可於物件上擴充）：

- `key_item_id`：可開此鎖的專用鑰匙物品 id（空則表示接受任何解鎖工具或僅能破壞／劇情解鎖）。
- 解鎖工具：物品表內可定義具「解鎖工具」屬性的物品（如 `unlock_tool: true` 或 `item_type: "unlock_tool"`），持有該類物品時可對上鎖物件執行 Unlock；若物件有 `key_item_id`，則鑰匙與解鎖工具皆可開鎖。
- `break_lock_noise`：破壞鎖時是否產生可被聽聞的聲響（同房／鄰房事件）。
- `break_lock_damage`：破壞後敘事（例：「鎖頭被撬壞，門板留下一道裂痕。」）。

**範例：上鎖的庫房門**

```json
{
  "id": "life_storage_door",
  "name": "庫房門",
  "owner": "inn",
  "sockets": ["Look", "Open", "Unlock", "BreakLock", "Operate"],
  "state": "locked",
  "key_item_id": "key_life_storage",
  "break_lock_noise": true,
  "responses": {
    "Look": "一扇厚實的木門，門閂上掛著一把銅鎖。"
  },
  "state_responses": {
    "locked": {
      "Open": "門被鎖住了，紋絲不動。",
      "Unlock": "你以鑰匙（或解鎖工具）打開銅鎖，門閂一鬆。",
      "BreakLock": "你硬生生撬開鎖頭，門板發出刺耳的刮擦聲。",
      "Operate": "你需要鑰匙才能開鎖。"
    },
    "closed": { "Open": "你推開了門。", "Operate": "你將門閂推上。" },
    "open": { "Look": "門大開著，門後是堆滿雜物的庫房。" }
  }
}
```

**與歸屬權的關係**：對有主之物的門/櫃執行 **BreakLock**，等同未授權的破壞行為；若看守者在場會被阻止，四下無人則可能記入偷竊/破壞事件。

## 十、實作路線

### 第一步：純觀看（最小可行）✅ 已完成

1. 各房間 JSON 內含 `objects` 陣列，`Look` / `Read` / `Smell` 等插座；模板與欄位說明見 `data/rooms/README.md`
2. 後端由 store 載入房間時讀取 `objects`，main 呼叫 `db.SetObjectsForRoom` 註冊；查詢用 `db/room_object` 快取
3. `RoomViewMsg` 新增 `Objects []ViewObject`，`handleDoAction` 支援物件與依名稱查詢
4. 房間 `description` 以 `〔物件名〕` 標記，前端 `formatDesc` 解析為 `.desc-object`
5. **點擊即觀看**：點描述物件或人物欄 NPC 即送 Look，觀看敘事顯示於 Log
6. **Log 下一行其他動作**：main.js 在觀看後 append 【閱讀】【對話】【攻擊】等可點擊列（`.log-object-actions` / `.log-object-action`），人物欄取消手風琴

### 第二步：歸屬權 + 偷竊

1. `handleDoAction` 加入歸屬權判定流程（§4.2）
2. 「四下無人」判定函式
3. 偷竊事件寫入日誌
4. NPC 看守者的阻止反應（使用 NarrateMsg）
5. 各房間 JSON 的 `objects[]` 補充 `owner_guard` / `use_blocked` / `use_steal`（欄位與後端尚未實作）

### 第三步：有狀態物件

1. 物件狀態持久化（例：store/JSON，如 data/runtime 或專用檔）
2. 狀態轉移邏輯
3. 狀態感知的 Sockets 回傳（不同狀態開放不同動詞）
4. **上鎖物件**：Unlock（需對應鑰匙或解鎖工具）、BreakLock（破壞鎖，可選聲響／損壞敘事），見 §9.3

### 第四步：物件環境敘事

1. 物件 ambient 池接入 idle tick
2. 與 NPC 閒置動作混合，同一房間的物件和 NPC 交替產生環境敘事

### 第五步：互動產出

1. Use → 製作/產出（對接經濟系統）
2. Take → 採集（背包系統）
3. Open → 掉落（物品表）

### 導航與出口融合（§2.3，依 UI 排程）

1. **點擊分流**：前端依物件 `sockets` 決定點擊行為——巷道／路段類（以 Move 為主）點擊即送 `Move`；建築／商鋪類先送 `Look`，Log 再顯示【進入】等。
2. **exits 與 UI**：`exits` 保留完整供 NPC 尋路；可選 `ui_hidden: true`，前端出口欄過濾隱藏項；或完全取消出口欄，改由描述內 `〔〕` 與物件驅動移動。
3. **後端 Move**：對物件執行 `Move` 時，依物件之 `move_to_room_id`（或與該房 `exits[].to` 對應）執行玩家切房。
